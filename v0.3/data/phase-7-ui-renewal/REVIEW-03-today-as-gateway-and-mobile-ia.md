## 1. 문제 제기 — 기존 IA의 두 가정이 틀렸다

기존 설계(00 결정 A2)는 5+1 의도 기반 IA(Today/Story/Library/Plan/Coach + Data)를
채택했다. 이 결정에는 두 암묵 가정이 있었고, 둘 다 재검토가 필요하다.

- **가정 1 (사용자 유형 분리)**: 사용자를 "계획 따르는 러너 / 상태 보는 러너"
  등으로 나눠 화면을 배분할 수 있다.
  → **틀림**. 한 사용자 안에 모든 모드가 시점마다 다르게 켜진다. 계획 러너도
  상태를 보고 과거를 뒤지며, 가볍게 들어온 러너도 브리핑을 보면 훈련·목표
  욕심이 생겨 데이터를 파고든다. 유형이 아니라 **하나의 사용자의 가변적 의도**다.

- **가정 2 (데스크탑형 탭 IA)**: 의도별로 탭을 나란히 두면 사용자가 자기 의도에
  맞는 탭을 고른다.
  → **모바일에서 약함**. 대부분 모바일 접속이며, 엄지 도달·인지 비용 측면에서
  5탭은 과하다. 탭을 "고르게" 하는 것 자체가 마찰이다.

## 2. 핵심 재정의 — Today is a Gateway

Today는 "오늘 뭐 할지 알려주는 코치 화면"도, "상태 보여주는 대시보드"도 아니다.

> **Today = 사용자를 어느 깊이에 있든 받아주고, 한 단계 더 깊은 관여로
> 끌어당기는 관문.**

아무 의욕 없이 들어와도 의미 있는 브리핑 하나는 건지고, 그 브리핑이
"내 상태가 이렇구나 → 그럼 뭘 하지 → 계획을 세워볼까 → 이 숫자는 왜 이렇지"로
자연스럽게 끌고 들어가는 **미끄럼틀**이어야 한다.

목업 v3의 "근거 계층(파고들기)"은 미끄럼틀의 *수직 방향*(아래로 드릴다운)만
구현했다. 빠진 두 축을 추가한다:
- **수평(넓히기)**: 상태 → 활동 → 훈련 → 계획 → 성장으로 관심사 이동.
- **수직 상향(끌어올리기)**: 무관심 → 관여로의 전환. ← **이것이 Today의 존재 이유**.

## 3. 설계 모델 — 계층적 관여 (Progressive Engagement)

Today 한 화면을 깊이가 다른 층으로 쌓는다. **세로 스크롤 = 관여 깊이.**
각 층은 다음 층으로 끌어당기는 "후크"를 가진다. 이 세로축이 기존 옆 탭들의
기능을 흡수하므로 탭 수를 줄일 수 있다.

| 층 | 누가 보나 | 콘텐츠 (블록) | 다음 층으로의 후크 |
|----|----------|--------------|-------------------|
| **L0 — 즉시 브리핑** | 0초, 누구나 | 오늘 한 줄 판단/브리핑, Readiness 한눈에, 동기화 상태 | "왜?" → L1 근거 |
| **L1 — 내 상태 요약** | 관심 생기면 | 회복(HRV·수면·바디배터리), 어제/최근 활동 요약, 주간 누적 진행(거리·시간·TSS) | 활동/지표 탭 → L3 드릴, "이번 주 흐름" → L2 |
| **L2 — 흐름·훈련·성장** | 욕심 생기면 | 성장 내러티브(Story 흡수), 계획 준수율·다음 세션(Plan 흡수), AI 제안 | "계획 세우기" → Coach, "전체 추세" → L3 |
| **L3 — 데이터 드릴다운** | 파고들면 | 781 지표 트리, provider 비교, 출처·공식·재계산(AO-1/3), 원본 | Library 영역으로 연속 |

핵심: **Story 진입점과 Plan 현황이 Today 세로축으로 흡수**된다. 단 Plan의 수립·수정 작업은 별도로 Coach 탭이 담당한다(§4 참조). Story·Plan은 더 이상 독립 탭이 아니다.

## 4. 모바일 IA 재설계안 — 확정
원칙: 탭은 적을수록 좋다. 세로 관여축이 흡수한 만큼 하단 탭을 줄이고, 관리성 항목은 하단 탭이 아니라 상단 3선(햄버거) 메뉴로 분리한다.

확정 구조: 하단 3탭 + 상단 3선
하단 탭 3개: Today · Library · Coach.
Today: L0~L2 관문(브리핑·상태·흐름). Story·Plan 현황을 흡수.
Library: L3 데이터 전체(781 지표·활동·provider 비교·드릴다운).
Coach: 단순 Q&A가 아니라 작업 목적지(destination). 목표 셋업, 훈련 계획 수립·비교·수정, 상태 기반 조정을 수행. 여러 단계의 본격 작업 흐름이므로 플로팅이 아닌 독립 탭이 적합하며, RunPulse의 간판 기능이므로 발견성을 위해 상시 노출한다.
상단 3선 메뉴(관리 서랍): 자주 쓰지 않는 항목만 — 설정, 데이터 소스 연결, 내보내기/백업, 계정, 로그아웃. 자주 쓰는 핵심 기능은 절대 3선에 숨기지 않는다. 3선은 "기능 탭의 대체물"이 아니라 "관리·설정 서랍"이다.
검토 기록 (확정 근거)
당초 안 A(2탭+Coach 플로팅)를 검토했으나, Coach가 단순 대화가 아니라 목표·계획 수립·조정까지 포함하는 워크플로우 허브임이 확인되어 폐기. 플로팅 버튼은 "짧게 부르고 닫는" 가벼운 대화용 패턴이라, 다단계 작업 흐름과 전체 화면이 필요한 Coach에는 부적합. Coach는 위젯이 아니라 목적지이므로 독립 탭으로 확정. "더보기 탭"은 하단 한 칸을 소모하므로 쓰지 않고, 부가 항목은 상단 3선으로 빼 하단을 비운다.

Plan의 분리
Coach가 계획 수립·수정을 맡으므로 기존 독립 화면 Plan(/plan)을 둘로 나눈다. 계획 현황 보기(준수율·다음 세션)는 Today L2 블록으로 흡수하고, 계획 수립·수정 작업은 Coach 탭에서 수행한다. = 보는 것(Today)과 만드는 것(Coach)의 분리.

데스크탑
모바일에서 흡수·분리한 영역은 데스크탑에서 사이드바·우측 패널로 펼쳐 보일 수 있다. IA는 하나, 표현은 뷰포트별로 다르게(반응형 IA).

## 8. 배포 모델 확정 — SaaS, 서버 가공, 데이터 소유권 유지

**확정 사실 (제품 성격)**
- RunPulse는 **SaaS**다. 데이터는 VPC 내에서 API로 백그라운드 수집되고,
  ML 학습·분석·훈련 계획 생성 등 가공은 **서버에서 일어난다**. 이건 우회 불가
  — 통합·ML·계획의 가치 자체가 서버 가공을 전제한다.
- 향후 native/PWA로 단말 수집을 더할 수 있으나, **가공 책임은 서버에 남는다.**
- **인증 현황**: 현재 정식 로그인 기능 없음. Cloudflare Access로 GitHub email을
  로그인 대체로 사용. DB는 `email@db` 파일 단위로 사용자별 분리 저장.
- **인증 로드맵**: 향후 Google/Apple OAuth 정식 회원가입 오픈 예정.

**P8(Local-First Identity) 재해석 — 충돌이 아니라 갱신**
P8의 원문은 "데이터는 로컬에"였으나 SaaS와 모순된다. 다음으로 갱신한다:

> **P8' — Data Ownership & Transparency (데이터 소유권·투명성)**
> 데이터는 서버에서 가공되더라도, (1) 사용자별로 격리 저장되고
> (`email@db`), (2) 언제든 전체 export/백업 가능하며, (3) 외부 LLM/ML에
> 전송되는 데이터 범위가 투명하게 고지되고, (4) 원본(source_payloads)이
> 보존되어 재가공·이식이 가능하다. = "클라우드에 있되 내 것이다."

UI 함의: "로컬 DB" 문구 대신 "내 데이터 · 격리 저장 · 언제든 내보내기"로
표현. AI 전송 범위 고지는 그대로 유지(P8 준수 예시 재활용).

## 9. 사용자 생애주기 — 비로그인부터 데이터 충만까지

관문(Today)은 데이터 충만 사용자만의 것이 아니다. SaaS는 **전체 생애주기**를
설계해야 한다. 각 단계는 다음 단계로 끌어올리는 후크를 가진다.

| 단계 | 상태 | 화면/목표 | 다음 단계 후크 |
|------|------|----------|---------------|
| **S0 — 방문자** | 비로그인 | **공개 랜딩**: RunPulse 가치 증명(통합·투명·근거·계획). 정직한 데모. | "내 데이터로 보기 → 가입" |
| **S1 — 가입/연결** | 로그인, 데이터 0 | OAuth(현재 GitHub/CF, 향후 Google/Apple) → 소스 연결 유도 | 소스 1개 연결 → S2 |
| **S2 — 콜드 스타트** | 연결됨, 백필 중/소량 | 백필 진행 표시 + 들어오는 데이터 즉시 의미화 | 데이터 도착 → S3 |
| **S3 — 데이터 충만** | 통합 완료 | Today 관문 (REVIEW-03 §3 계층적 관여) | 드릴다운·계획·성장 |

### 9-1. S0 공개 랜딩 — 비로그인 방문자

목표: 로그인 폼만 던지지 않는다. **가치를 먼저 증명**하고 가입으로 끌어들인다.
- RunPulse 차별점을 화면으로: "4개 소스 → 하나로", "모든 숫자는 근거까지
  파고들 수 있다", "시간이 아니라 상태에 묶인 계획".
- **정직한 데모**: 가짜 개인 데이터로 속이지 않는다. "샘플 러너 Alex의 데이터"
  처럼 **명시적 데모 데이터**로 드릴다운·근거 계층을 실제 체험하게 한다
  (P1·P2를 로그인 전에 미리 맛보임).
- 초보 러너 후크: "아직 트래커가 없어도 괜찮아요 — 연결하면 과거 기록부터
  분석해 드립니다" / "오늘부터 기록해도 첫 주부터 의미가 보입니다".
- CTA: "GitHub/Google로 시작하기" (현 CF 인증 → 향후 OAuth).

### 9-2. S2 콜드 스타트 — 데이터 0~소량 (가장 어려운 구간)

RunPulse의 가치는 데이터가 쌓여야 나오는데 초보·신규는 데이터가 없다.
이 구간을 버티게 하는 설계:
- **백필 우선**: 소스 연결 즉시 과거 활동을 백그라운드 수집(이미 트래커 쓰던
  사용자에겐 "작년 기록이 다 분석됐다"는 즉각적 보상).
- **진행의 가시화**: "Garmin에서 312건 가져오는 중 · 184건 분석 완료"처럼
  쌓이는 과정 자체를 콘텐츠로. 빈 화면이 아니라 "채워지는 화면".
- **소량 데이터 의미화**: 활동 1건만 있어도 보여줄 것(페이스·HR·존·근거 1개)을
  설계. 지표가 아직 없으면 "N건 더 모이면 CTL 계산 시작" 같은 **미래 약속**으로
  빈 자리를 채움 (빈 상태가 아니라 예고).
- **트래커 없는 진짜 초보**: 수동 기록/체크인(QuickInput)부터 시작 → "첫 주
  요약" 같은 작은 성취로 관여 유지.

### 9-3. 빈 상태(empty state) 원칙

모든 화면은 "데이터 충만" 버전과 "데이터 0/소량" 버전을 **쌍으로** 설계한다.
빈 상태는 죽은 화면이 아니라 다음 행동으로 유도하는 화면이다 (연결/기록/대기).

### 9-4. 4-State 동시 설계 결정
S0~S3은 별도 화면이 아니라 **Today 관문의 상태 변형(state variant)**이다. S0(비로그인 데모)·S2(콜드스타트)는 결국 "데이터가 적거나 없을 때 Today가 어떻게 보이는가"의 문제이며, S3 Today의 empty-state 변형으로 동일 컴포넌트를 공유한다. 따라서 Today를 처음부터 4-state(S0 비로그인 / S2 콜드스타트 / S2.5 소량 / S3 충만)로 함께 설계한다. 단 구현 순서는 S3 → S2 → S0로 두어 Phase 7 범위 폭증을 막는다. S3만 만들고 S0~S2를 OAuth 시점으로 미루지 않는 이유: S0(비로그인 랜딩)은 SaaS 유입 깔때기의 시작점이며, S2와 함께 S3 컴포넌트를 재사용하므로 동시 설계가 재작업을 줄인다.

## 10. §5 연쇄 영향에 추가

- **02 정보구조**: 인증 상태(비로그인/로그인)별 라우팅 분기 추가. 공개 라우트
  (랜딩·데모) vs 보호 라우트.
  하단 3탭(Today/Library/Coach) + 상단 3선(관리 서랍) 구조 확정. Plan 라우트는 현황(Today)과 작업(Coach)으로 분할. Story 독립 라우트 제거.
- **03 화면카탈로그**: S0 랜딩, S1 연결, S2 콜드스타트 화면 신규. 모든 핵심
  화면에 빈 상태 변형 추가.
- **01 원칙**: P8 → P8'(데이터 소유권·투명성) 갱신.
- **05 기술아키텍처**: OAuth(Google/Apple) 로드맵, CF Access 현황,
  `email@db` 격리 저장을 인증/멀티테넌시 섹션으로 명문화.
