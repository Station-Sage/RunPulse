## 이 문서의 목적

`00` 문서에서 확정된 8개 원칙의 상세 정의를 기록한다. 각 원칙은 다음을 포함한다.

- **정의** — 원칙이 요구하는 것
- **근거** — 비전에서 이 원칙을 요구하는 이유
- **적용** — 화면·컴포넌트 설계 시 구체적 판단 기준
- **위반 예시** — 이 원칙을 어기는 설계의 모습
- **준수 예시** — 이 원칙을 따르는 설계의 모습

모든 화면·컴포넌트 설계 결정에서 이 8개 원칙이 판단 기준이 된다. 원칙 간 충돌이 발생하면 이 문서에서 정의한 우선순위 순서로 해결한다.

## P1 — Evidence-First (근거 우선)

### 정의

모든 결론·권장·점수·경고는 근거 인용 슬롯을 동반한다. 근거는 클릭 가능하고 원천 데이터로 점프한다.

### 근거

비전 원칙 3("맥락 있는 안내")의 핵심 요건이다. "오늘 쉬어라"는 말과 "ACWR 1.4, HRV -15%, 수면 54점이기 때문에 오늘 쉬어라"는 말은 전혀 다른 경험을 만든다. 러너가 근거를 볼 수 있을 때 조언을 수용하거나 거부하는 자율적 판단이 가능하다. 7장 KPI: AI 답변에 평균 2개 이상 근거 인용, 근거 추적 가능성 100%.

### 적용

- AI 코치 응답, 권장 카드, 점수 설명 — 근거 인용 없이 결론만 제시 금지
- 근거 인용은 `<EvidenceQuote>` 컴포넌트로 렌더 (클릭 가능한 칩)
- 칩 클릭 시 우측 패널 또는 모달에서 원천 데이터 표시
- 근거 개수: 최소 2개, 권장 3개. 단순 상태 표시는 1개도 허용
- "왜?"를 누르지 않아도 근거가 보인다 — 숨겨진 근거는 없는 것과 같다

### 위반 예시

```
❌ "오늘은 이지런을 권합니다."
❌ UTRS: 62 (점수만 표시, 구성 요소 없음)
❌ "부상 위험 높음" (어떤 지표가 올라갔는지 없음)
```

### 준수 예시

```
✓ "오늘은 이지런을 권합니다.
   근거: [ACWR 1.38↑] [HRV -15%] [수면 54점]"
   → 각 칩 클릭 시 해당 지표의 7일 추세 차트로 점프

✓ UTRS: 62
   [CTL 58 × 0.4] [ATL 71 × 0.35] [HRV -8% × 0.25]
   → 각 항목 클릭 시 계산 분해 펼침

✓ "부상 위험 상승 (CIRS 3단계)
   근거: [ACWR 1.38] [케이던스 비대칭 +7%] [종아리 통증 보고 3일 전]"
```

## P2 — Drillable Everything (어디든 드릴다운)

### 정의

모든 메트릭과 차트는 한 번의 인터랙션 안에서 계산 분해와 원천 데이터까지 도달 가능하다.

### 근거

비전 원칙 2("투명한 분석")의 구현이다. 8장의 핵심 요구: *"PMC만 보여주는 것이 아니라, PMC를 구성하는 모든 활동의 모든 메트릭이 한 번의 클릭으로 도달 가능."* 블랙박스 점수는 신뢰를 만들지 못한다. 러너가 "이 숫자가 어디서 왔는가"를 볼 수 있을 때 RunPulse의 분석을 코치가 아닌 **자신의 데이터로 돌아가는 도구**로 인식하게 된다.

### 적용

- 모든 메트릭 값 — 클릭/탭으로 계산 분해 진입 가능
- 모든 차트 — 데이터 포인트 클릭 시 해당 날짜/활동 상세로 진입 가능
- 드릴다운 깊이: 최대 3단계 (요약 → 계산 분해 → 원천 raw 데이터)
- 드릴다운 UI: 우측 패널(데스크탑), 슬라이드업 시트(모바일)
- 컴포넌트는 드릴다운 목적지(`drillTarget`)를 항상 가져야 한다

### 위반 예시

```
❌ CTL: 64 (클릭해도 아무 일 없음)
❌ PMC 차트에서 특정 날짜 클릭 — 반응 없음
❌ 합성 메트릭 UTRS: 57 (구성 요소로 분해 불가)
❌ "이 활동의 VO2max: 48.3" — 계산 방식 확인 불가
```

### 준수 예시

```
✓ CTL: 64 클릭
  → "CTL은 지난 42일간 일일 TRIMP의 지수가중이동평균입니다.
     오늘 기준 CTL = 이전 CTL × e^(-1/42) + 오늘 TRIMP × (1 - e^(-1/42))
     [최근 42일 TRIMP 차트 표시]"
  → "오늘 TRIMP: 58" 클릭 → 해당 활동 상세로 이동

✓ PMC 차트 6월 3일 포인트 클릭
  → "CTL 58 / ATL 71 / TSB -13
     이 날의 활동: [서울숲 템포런 12km]" 클릭 → 활동 상세 이동
```

## P3 — Provider Transparency (출처 투명성)

### 정의

메트릭 값 옆에는 항상 provider가 표시되거나, 한 번의 인터랙션 안에서 확인 가능하다. 동일 메트릭의 타 provider 값과 비교 가능하다.

### 근거

RunPulse의 핵심 자산은 4개 소스 통합이다. 이 통합이 UI에서 보이지 않으면 "왜 4개 소스를 연결해야 하는가"라는 질문에 답하지 못한다. 9장 정체성 요구: *"어느 메트릭이 어느 provider에서 왔고 RunPulse가 어떻게 합성했는가를 한 페이지에 보여주는 화면이 RunPulse 정체성의 표현물."* 또한 provider 간 값이 다를 때 러너가 그 차이를 인식하고 판단할 수 있어야 한다.

### 적용

- `<MetricCell>` 컴포넌트는 provider 배지를 기본 포함 (Garmin/Strava/Intervals/Runalyze/RunPulse)
- primary provider 값 표시 + 호버/탭 시 타 provider 값 비교 표시
- "RunPulse 계산" 메트릭은 명시적으로 RunPulse 배지 부착
- provider 우선순위가 왜 이 provider인지 설명 가능해야 함
- Library 영역: 시맨틱 그룹 13개 × provider 4개 매트릭스를 일급 화면으로 구성 (P2-003)

### 위반 예시

```
❌ VO2max: 47.3 (어느 소스인지 불명)
❌ 수면 점수: 74 (Garmin인지 Runalyze인지 모름)
❌ 동일 메트릭을 두 provider가 제공하는데 하나만 표시
```

### 준수 예시

```
✓ VO2max: 47.3 [Garmin]
  탭 시: "Garmin: 47.3 / Runalyze: 46.8 / RunPulse: 47.1
         Primary: Garmin (이유: 가장 최근 측정, ADR-006)"

✓ 안정시 심박: 48 bpm [Garmin]
  → "Garmin 7일 평균. Whoop 연동 시 Whoop 값이 primary가 됩니다."
```

## P4 — Intent-Centered IA (의도 중심 IA)

### 정의

정보 구조는 기능 분류가 아니라 사용자 의도로 조직된다. 매 진입에 사용자는 자기 의도와 매핑되는 영역으로 즉시 도달한다.

### 근거

현재 7탭 IA는 기능 분류(활동/레포트/훈련/AI코치...)로 구성되어 "지금 나는 어떤 탭을 열어야 하는가"라는 인지 비용을 만든다. 비전 페르소나의 핵심 질문 3가지 — "오늘 무엇을 할까", "내 상태는 어떻게 변하고 있나", "왜 이 숫자가 이런가" — 각각이 한 영역으로 즉시 매핑되어야 한다.

### 적용

| 사용자 의도 | 영역 |
|------------|------|
| 오늘 무엇을 할까 | Today |
| 내 상태는 어떻게 변하고 있나 | Story |
| 왜 이 숫자가 이런가 | Library |
| 다음 레이스를 어떻게 준비할까 | Plan |
| 내 코치와 대화하고 싶다 | Coach |
| 데이터 관리/연결/설정 | Data |

- 탭 레이블은 의도를 나타내는 동사형 또는 명사형 (기능명 금지)
- 진입 화면은 "이 영역에서 무엇을 할 수 있는가"를 3초 안에 전달
- 영역 간 이동은 컨텍스트를 유지한다 (Today에서 Library로 이동 시 관련 메트릭이 열린 상태로 도달)

### 위반 예시

```
❌ "레포트" 탭 (기능 분류)
❌ "설정" 탭 (운영 기능을 일급 시민으로 표시)
❌ 활동 카드에서 메트릭 분석으로 이동 경로 없음
❌ AI 코치 탭에서 훈련 계획 수정 불가 (영역 간 단절)
```

### 준수 예시

```
✓ 하단 네비게이션: Today / Story / Library / Plan / Coach
  (Data는 더보기 메뉴 또는 설정 아이콘)

✓ Today에서 UTRS 57 클릭
  → Library/metrics/utrs 로 컨텍스트 이동 (계산 분해 즉시 표시)

✓ Coach 대화 중 "이번 주 ACWR 차트 보여줘"
  → 우측 패널에 차트 표시 (Library로 이동하지 않고 인라인)
```

## P5 — Quiet Data (조용한 UI, 시끄러운 데이터)

### 정의

UI 장식은 절제하고 데이터의 시각적 잉크가 가장 강하다. 정보 밀도와 위계는 타이포그래피·여백·분할선으로 만든다.

### 근거

현재 UI의 글래스모피즘(backdrop-filter, 반투명 레이어, 네온 그라데이션)은 도구 UI에서 데이터보다 컨테이너가 더 눈에 띄는 역전을 만든다. Tufte의 data-ink ratio 원칙: 잉크의 최대 비율이 데이터를 나타내야 한다. 레퍼런스: Linear, Stripe Dashboard, Vercel Analytics — 공통점은 UI가 "뒤로 물러나" 데이터가 전면에 나오는 구조다.

### 적용

**폐기**:
- 글래스모피즘 (backdrop-filter, 반투명 카드)
- 장식적 그라데이션 (배경, 버튼, 카드)
- 네온 액센트 컬러 (시안, 네온그린)
- 의미 없는 모션 (hover glow, 등장 애니메이션)

**채택**:
- 디자인 토큰 기반 컬러 시스템 (의미론적 컬러만 사용)
  - 등급 컬러 5단계: excellent / good / moderate / poor / danger
  - Provider 컬러 4종: Garmin / Strava / Intervals / Runalyze
  - 나머지는 중립 회색 스케일
- 타이포그래피 위계: Inter Variable (본문) + JetBrains Mono (숫자)
- 정보 구분: 여백 + 1px 분할선 (카드 박스 최소화)
- 모션: 데이터 변경 시 트랜지션만 (장식 모션 없음)
- Story 영역 예외: 에디토리얼 타이포그래피 허용

### 위반 예시

```
❌ backdrop-filter: blur(20px) 카드
❌ background: linear-gradient(135deg, #1a1a2e, #16213e) 장식 배경
❌ 네온 그린 액센트 버튼
❌ 카드 등장 시 fade-in + translateY 애니메이션
❌ 메트릭 값보다 카드 테두리 그림자가 더 눈에 띄는 레이아웃
```

### 준수 예시

```
✓ 흰 배경(라이트) / #0f0f0f 배경(다크) + 중립 회색 텍스트 위계
✓ CTL 64 → JetBrains Mono 32px bold, 단위 18px regular
✓ 섹션 구분: 1px border-color: var(--border) 한 줄
✓ "excellent" 상태 → var(--grade-excellent): #22c55e 텍스트 컬러만
✓ 데이터 포인트 클릭 시 200ms ease 트랜지션 (패널 슬라이드)
```

## P6 — One Finger Reach for Input (입력은 한 손가락 거리)

### 정의

RPE·통증·노트 입력은 모든 핵심 영역에서 한 손가락 거리에 있다. 입력 마찰을 최소화한다.

### 근거

7장 KPI: 활동의 60% 이상에서 사용자 입력(RPE/통증) 수집. 이 목표는 입력 UI가 "찾아야 하는 것"이면 달성 불가능하다. Axis 4(5.3)의 수동 데이터 입력 원칙: "30초 이내로 완료할 수 있는 간단한 체크인". 입력 데이터는 AI 코치 컨텍스트(Layer 1, Layer 2)의 핵심 재료이므로 수집률이 AI 코칭 품질을 직접 결정한다.

### 적용

- `<QuickInput>` 컴포넌트가 Today / Activity 상세 / Coach / Library에 항상 노출
- 활동 카드에서 RPE 입력: 카드 내 슬라이더, 별도 화면 이동 없음
- 통증 입력: 바디맵 탭 한 번 (위치 선택) + 강도 선택 (1~3)
- 메모: 텍스트 입력, 선택사항
- 전체 입력 플로우: 최대 3 탭 이내 완료
- 키보드 단축키 지원 (데스크탑): R → RPE, P → 통증, N → 노트

### 위반 예시

```
❌ 활동 기록 후 RPE 입력 경로: 활동 상세 → 더보기 → 메타데이터 → RPE 탭
❌ 통증 보고를 별도 "건강 일지" 메뉴에 숨김
❌ 입력 완료 후 저장 확인 모달 (불필요한 단계)
❌ Today 화면에 RPE 입력 없음
```

### 준수 예시

```
✓ 활동 카드 하단 고정 영역:
  [RPE: ● ● ● ○ ○] [통증 없음 ✓] [메모 추가...]
  → 카드 자체에서 탭 한 번으로 각 항목 수정

✓ Today 화면 상단:
  "오늘 컨디션: [●●●●○] 어디 아픈 곳 있나요? [없음]"
  → 10초 체크인

✓ Coach 대화창 하단:
  [오늘 RPE 기록] 버튼 — 대화 맥락에서 즉시 입력 가능
```

## P7 — State-Bound Plan (상태에 묶인 계획)

### 정의

훈련 계획은 시간이 아니라 러너의 상태에 묶인다. 모든 계획 UI는 적응 가능성을 시각화한다.

### 근거

비전 A.6(적응형 프로그램 실행): *"기존 앱의 '12주 플랜'은 시간에 묶여 있지만, RunPulse의 플랜은 러너의 상태에 묶여 있습니다."* "12주 하프마라톤 플랜"을 PDF처럼 뽑아주는 것은 RunPulse의 정체성과 정반대다. 계획이 상태를 반영하지 않으면 ACWR 1.4 상태에서도 "오늘 인터벌 6×1km"를 시키는 결과가 된다.

### 적용

- 계획 화면에서 "오늘 예정 세션"은 항상 현재 ACWR/HRV/TSB와 함께 표시
- 세션 옆에 "상태 기반 조정 제안" 항상 노출 (비활성화 가능하되 기본 ON)
- 주간 계획 뷰: 고정된 날짜표가 아니라 "이번 주 남은 부하 예산" 기반 레이아웃
- 위상 전환(Base→Build) UI: "예정일 D-3"이 아니라 "CTL 목표 45 달성 시" 기준
- 프로그램 비교 뷰: 시간 단위(12주) 옆에 상태 단위(CTL +12, 완주 확률) 병기

### 위반 예시

```
❌ "6주차 화요일: 인터벌 8×400m" (상태와 무관하게 고정)
❌ 주간 달력 뷰에 현재 TSB/ACWR 표시 없음
❌ 오늘 HRV 기저선 -20%인데 예정 세션 변경 제안 없음
❌ "11주 후 Build Phase 시작" (날짜 기준 고정 전환)
```

### 준수 예시

```
✓ 화요일 인터벌 세션 카드:
  "인터벌 6×1km @I페이스
   현재 상태: ACWR 1.21 / HRV +2% / TSB -8
   → 정상 범위. 예정대로 진행 권장."

✓ 상태 악화 시 같은 카드:
  "인터벌 6×1km @I페이스
   현재 상태: ACWR 1.38 / HRV -15% / TSB -19
   → ⚠ 부하 축소 권장: 4×1km으로 변경하거나 이지런 대체"
   [세션 수정] [대체 세션] [예정대로]

✓ Build Phase 전환 트리거:
  "CTL 목표 45 달성 시 Build Phase로 진입합니다.
   현재 CTL: 41 / 진행률 91%"
```

## P8 — Local-First Identity (로컬 퍼스트 정체성)

### 정의

UI 어디서도 클라우드 종속을 느끼게 하지 않는다. 데이터 소유권이 표현된다. Export·snapshot·원본 보존이 일급 기능이다.

### 근거

비전 8장 차별화 전략: *"클라우드 종속이 아님 — 데이터는 로컬에, 사용자 소유."* 9장 5년 후 비전: "이 앱 하나로 충분한가? Yes"가 진실이 되려면, 데이터가 여기 있고 내 것이라는 감각이 UI에서 느껴져야 한다. 분기점 B에서 "단일 프로세스 배포 가능성"을 제약으로 박은 것도 같은 이유다.

### 적용

- Data 영역: "내 데이터" 섹션이 설정보다 우선 (export/snapshot/raw 접근)
- 마지막 동기화 시간 항상 표시 — 클라우드 의존성이 아닌 "내 로컬 DB 최신화" 감각
- 오프라인 상태에서도 핵심 뷰(Today, Library, 최근 활동) 접근 가능
- "이 데이터가 저장된 위치" 언제든 확인 가능
- AI 호출 시 "외부 API에 전송되는 데이터 범위" 투명하게 표시
- Tauri 데스크탑 패키징 대비: 네이티브 파일시스템 접근을 가정한 UI 구조

### 위반 예시

```
❌ "클라우드에서 불러오는 중..." (로딩 메시지에서 클라우드 강조)
❌ Export 기능이 설정 메뉴 깊은 곳에 숨겨짐
❌ 오프라인 시 모든 화면 "연결 필요" 표시
❌ AI 코치 대화 시 "분석 서버에 전송 중" 진행 표시
```

### 준수 예시

```
✓ 상단 바 우측: "DB 동기화: 2시간 전" (로컬 DB 감각)
✓ Data 영역 첫 화면:
  [내 데이터 내보내기] [원본 백업 다운로드] [소스 연결 관리]
  (설정보다 데이터 소유권이 앞에 위치)

✓ Coach 대화창 설명:
  "AI 코치는 외부 LLM API를 사용합니다.
   전송 데이터: 요약 지표(CTL/ATL/VDOT 등), 최근 활동 목록
   원본 GPS/스트림 데이터는 전송되지 않습니다."

✓ 오프라인 시:
  Today, Library(최근 30일), 활동 상세 — 정상 접근
  "Coach는 인터넷 연결이 필요합니다." (부분 제한만)
```

## 원칙 간 충돌 해결 예시

### 예시 1: P5(Quiet Data) vs. P1(Evidence-First)

근거 인용 칩(`<EvidenceQuote>`)이 화면에 너무 많으면 데이터가 아니라 UI 요소가 시끄러워진다.

**해결**: 기본 표시는 2개까지, 나머지는 "근거 +N개 더" 토글로 접기. P1이 P5보다 우선이므로 근거 자체를 삭제하지 않는다.

### 예시 2: P6(One Finger Reach) vs. P5(Quiet Data)

QuickInput이 항상 노출되면 화면이 복잡해진다.

**해결**: QuickInput은 활동 카드 내 고정 위치(하단 바 형태), 최소한의 시각 처리. RPE 슬라이더는 숫자 없이 5단계 점으로만 표현. P6이 P5보다 우선이므로 숨기지 않는다.

### 예시 3: P7(State-Bound Plan) vs. P4(Intent-Centered IA)

계획 화면에서 "오늘 상태"를 보여주면 Today 영역과 중복된다.

**해결**: Plan 영역의 상태 표시는 계획 관련 지표만 (ACWR, TSB, 부하 예산). 웰니스 상세는 Today 영역에서 담당. 두 영역의 역할이 다르다 — Plan은 "지금 이 계획을 실행해도 되는가", Today는 "오늘 전반적인 컨디션".

## 체크리스트 — 화면 설계 완료 기준

새 화면이나 컴포넌트 설계를 완료할 때 아래를 확인한다.

```
P1 ☐ 결론/권장/점수가 있다면 근거 인용 슬롯이 있는가?
P2 ☐ 메트릭/차트는 클릭 시 드릴다운이 가능한가?
P3 ☐ 메트릭 값에 provider 표시 또는 한 번에 확인 가능한가?
P4 ☐ 이 화면은 하나의 명확한 의도에 답하는가?
P5 ☐ 컬러/그라데이션/모션이 데이터 표현 목적인가, 장식인가?
P6 ☐ RPE/통증 입력이 3탭 이내 도달 가능한가?
P7 ☐ 계획/세션 UI에 현재 상태(ACWR/HRV/TSB)가 함께 표시되는가?
P8 ☐ 오프라인에서도 이 화면이 동작하는가, 동작 안 한다면 이유가 명확한가?
```
