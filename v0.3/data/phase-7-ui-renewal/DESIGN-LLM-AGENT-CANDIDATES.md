## 1. 핵심 발견 — 식별 시점(10-07)과 현재 코드가 다르다

후보 8건 중 상당수는 BACKLOG 서술("템플릿 문장 조합", "키워드 분기")과 달리 **이미 LLM 경로가 있다**. 새로 만들기 전에 기존 계층을 확장하는 것이 맞다.

| # | 후보 | BACKLOG 가정 | 현재 코드(확인한 것) | 잔여 갭 |
|---|------|--------------|----------------------|---------|

| 8 | 레이스 전략·테이퍼 | 표만 | 해당 표면을 코드에서 찾지 못함 | 신규. 코스·날씨 데이터 보유 여부 TODO: 확인 필요 |

**공통 인프라는 이미 갖춰져 있다**:
- `ai_wording.py`(ADR-059): 표면 선언 → 캐시 조회·백그라운드 생성·검증(숫자 ⊆ 근거, 길이, 금지어, 마크다운)·건강정보 익명화·`src_hash` 불일치 시 규칙 문구로 자동 복귀.
- `claude_queue`/`provider_claude_queue.try_complete`: 요청 스레드가 기다리지 않는 큐 경로.
- `llm_budget.py`: 사용자·전역 일 상한(기본 200호출/30만 토큰), 분당 10, 동시 3, 80%에서 워밍 중단.
- `coach_consent`: provider·노트 제외·도구 허용·폴백 동의(D8).

→ 공통 제약 ①~⑥ 중 ①(규칙 폴백)·③(검증)·④(동의)·⑤(캐시·상한)는 **표면 선언만으로 승계**된다. 새로 설계할 것은 ②(근거 표시 UI 규약)와 "서술이 아닌 **제안**을 내는 에이전트"의 게이트뿐이다.

## 2. 후보 분류 — 서술형 vs 제안형 vs 대화형

| 유형 | 후보 | LLM 역할 | 위험 | 기존 패턴 |
|------|------|----------|------|-----------|
| 서술형(문장만) | 2·5·6·7·8 | 서버 값을 해석해 문단 생성 | 수치 왜곡(검증으로 차단), 비용 | ADR-059 표면: `Surface` 선언 + 템플릿 + basis |
| 제안형(상태 변경 가능) | 1 | 조정안을 구조화 출력, 규칙 게이트 통과분만 반영 | **높음**(계획 훼손·부상) | `plan_draft` 게이트 + `plan_replan_service.apply`(되돌리기 포함) |
| 대화형 | 3·4 | 도구로 조회하며 답변·후속 질문 | 도구 남용·지연 | `chat_engine` 체인(이미 구현) |

## 3. 제안 단계 (BACKLOG 우선순위 3→2→1을 현황에 맞게 조정)

BACKLOG의 3→2→1은 "신규 구축"을 전제했다. 3·2는 이미 구현돼 있으므로 **측정 → 갭 메우기 → 제안형 순**이 더 안전하다.

- **0단계 — 평가 기반(선행)**: 오프라인 골든 세트(실 DB 사본 기준 입력→기대 속성)와 사실 정합 점검 스크립트. 현재 검증은 "숫자 ⊆ 근거" 수준이라 *방향이 틀린 문장*(예: 컨디션이 나쁜데 "좋음")은 못 잡는다. 이를 보강하지 않고 서술형을 늘리면 품질 회귀를 알 수 없다.
- **1단계 — 서술형 표면 확장(#7 → #5 → #6)**: 위험 최저, `ai_wording` 재사용. 표면마다 선언 + 템플릿 + basis 반올림 규칙 + 규칙 문구 폴백 유지. 정적 `action_hint`는 사용자 검수 문구라 **폴백으로 보존**(BACKLOG 7 명시).
- **2단계 — Today·Coach 갭 보강(#2·#3·#4)**: 신규 구축이 아니라 근거(입력 지표·날짜) 노출, 도구 호출 횟수 상한, 캐시 TTL 정책 점검.
- **3단계 — 제안형(#1)**: `[P7-PLAN-ENGINE]`과 통합 설계 필요, 위험 최대라 마지막. `plan_draft` 게이트(날짜·종류 불변, 거리 ±15%)를 구조 조정으로 확장하는 범위와 램프율·감량 상한 검증이 핵심.
- **4단계 — 신규(#8)**: 코스·날씨 입력 데이터 존재 여부 확인 후 판단.

**IMPL 1단계 제안**: 0단계(평가 스크립트) + #7 표면 1개. 외부 API 실호출 없이 모킹(BACKLOG IMPL 항목 제약).

## 4. 제약 ①~⑥ 충족 방식

| 제약 | 방식 |
|------|------|
| ① 규칙 폴백 | 표면은 `src_hash` 불일치·검증 불합격 시 규칙 문구 반환(기존). 제안형은 저장하지 않으면 규칙 계획 그대로 |
| ② 근거 표시 | 표면 `basis`를 UI의 EvidenceQuote(P1)로 노출하는 규약 — **신규 설계 필요**(§5 Q4) |
| ③ 검증 | `ai_wording.validate` 재사용 + 0단계의 방향성 점검 추가 |
| ④ D8 동의 | `coach_consent`/`_consent_ok` 재사용, 표면별 `needs_consent` 선언 |
| ⑤ 캐시·상한 | `ai_outputs`(kind `w:<표면>`)·`llm_budget` feature scope. 표면별 상한 분리 여부는 §5 Q2 |
| ⑥ 계산 비위임 | 입력은 서버 계산 값만. 템플릿에 "새 수치 생성 금지" 명시, 검증이 강제 |

## 5. 사용자 결정이 필요한 갈림길 (DECISIONS.md `[P7-LLM-AGENT-CANDIDATES]`에 기록)
