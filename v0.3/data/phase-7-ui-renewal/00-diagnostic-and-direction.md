## 0. 이 문서의 목적

웹 UI 전면 리뉴얼에 착수하기 전, 다음 세 가지를 확정한다.

1. **현 UI가 비전과 어디서 어긋나는가** (GAP 진단)
2. **데이터 레이어가 비전을 받쳐줄 수 있는가** (적합도 진단)

## 1. 절대 잊지 않을 북극성 — Future Vision 0~1장 요약

### 1.1 정체성 — 세 문장

> RunPulse는 러너의 흩어진 데이터를 하나로 모아, 스스로 이해할 수 있는 언어로 번역하고, 더 나은 결정을 내릴 수 있게 돕는 **개인 러닝 인텔리전스 플랫폼**이다.

### 1.2 세 가지 원칙 — 모든 UI 결정의 판단 기준

1. **데이터 통합과 소유권** — 4개 소스가 하나의 정규화된 저장소에 모이고, 이 자산이 러너 본인의 것이라는 감각이 UI에서 느껴져야 함
2. **투명한 분석** — 모든 메트릭은 블랙박스가 아니라 계산 근거와 원천 데이터로 드릴다운할 수 있어야 함
3. **맥락 있는 안내** — 숫자 나열이 아니라 "그래서 무엇을 해야 하는가"에 답하되, 항상 근거를 동반해 러너가 수용/거부를 스스로 판단할 수 있게

### 1.3 되지 않을 것

- 소셜 네트워크가 아님 — Kudos/팔로워/리더보드 배제
- 라이브 GPS 트래커가 아님 — 실시간 기록 UI 배제, "달린 뒤의 세계"에 집중
- 경직된 PDF 플랜 생성기가 아님 — 정적 계획표 배제, 상태 기반 적응형
- **클라우드 종속이 아님** (8장 보강) — 데이터는 로컬에, 사용자 소유

### 1.4 타겟 페르소나

4개 탭(Garmin/Strava/Intervals/Runalyze)을 오가며 자기 상태를 스스로 조립하던 러너. 데이터는 좋아하지만 데이터 과학자는 아니고, 코칭은 원하지만 월 20만 원은 거부하는 사람. **"왜 쉬어야 하는지, 어떤 수치가 그 판단의 근거인지"를 함께 보고 싶어 하는 사람.**

## 2. 현재 UI 진단 — 비전 GAP

### 2.1 사실 인벤토리

- **기술 스택**: Flask + 서버 사이드 HTML 문자열 생성 (Jinja 거의 사용 안 함). CSS 250줄과 JS 300줄이 `helpers.py`에 인라인 박힘. 매 페이지마다 통째로 인라이닝.
- **뷰 모듈 규모**: `src/web/` 약 80개 Python 파일. 단일 화면을 g1~g7 카드별로 분할. 수평 분할이 극단적.
- **현재 IA**: 하단 7탭 + 1 개발자 탭. `홈 / 활동 / 레포트 / 훈련 / AI코치 / 동기화 / 설정`.
- **디자인 시스템**: 다크 보라/네이비 그라데이션 + 시안/네온그린/오렌지/레드 액센트 + 글래스모피즘(반투명 카드 + backdrop-filter). 타이포그래피 스케일 거의 정의되지 않음.
- **데이터 접근**: 뷰가 raw SQL을 직접 작성하는 곳이 40+ 군데. `BACKLOG.md`의 `AUDIT-SERVICE-LAYER`로 박제됨. Phase 5에서 요구한 `src/services/` 미구현.

### 2.2 비전 충족도

| 비전 요소 | 점수 | 진단 |
|---|---|---|
| 데이터 통합 표현 | 2/10 | 통합은 일어났지만 UI가 자랑하지 못함 |
| 투명한 분석 | 3/10 | 정의 툴팁만 있고 계산 분해·원천 추적 부재 |
| 맥락 있는 안내 | 4/10 | 권장은 있으나 첫 화면 일급 시민 아님, 근거 결합 약함 |
| 정체성 경계 | 6/10 | 대체로 지킴, 단 정적 플랜 UI는 재검토 필요 |
| 확장성 | 2/10 | 새 기능 슬롯이 IA에 없음, 카드 누적 구조 |
| 코드 아키텍처 | 2/10 | UI/데이터 분리 안 됨, 컴포넌트화 불가 |
| **평균** | **3/10** | 부분 개선이 아닌 전면 재설계 정당화 수준 |

### 2.3 빠진 일급 시민 — 비전이 요구하지만 IA에 자리 없는 것

1. **내러티브 인사이트** — "지난 N주 이야기" 시간축 스토리텔링 (비전 5.2)
2. **사용자 입력 인프라** — RPE/통증/메모/AI 피드백/메트릭 보정 (비전 5.3, 7장의 60% 도달률 KPI)
3. **다중 경로 프로그램 비교** — 3~5개 프로그램 병렬 비교 (비전 2.3 핵심 차별점)
4. **메트릭 드릴다운 화면** — "이 값이 어떻게 계산되었는가" 전용 화면 (8장의 "한 번의 클릭으로 도달" KPI)
5. **알림/푸시/PWA 경험** — manifest는 있으나 푸시·홈 화면·오프라인 미구현
6. **확장 슬롯** — Axis 1~4 미래 기능을 받을 IA 슬롯 부재

### 2.4 구조적 부채

1. HTML 생성과 데이터 로딩이 같은 함수 안에 섞여 있음 — 컴포넌트화 불가
2. CSS/JS가 Python 문자열에 인라인 — 디자인 토큰·점진적 로딩·시각 회귀 테스트 불가
3. 상태 관리가 서버 측 redirect 기반 — 인터랙티브 드릴다운 불가
4. UI 컴포넌트 단위 테스트 불가
5. 모바일·접근성·국제화 거의 미고려

### 2.5 한 문장 진단

> 현재 RunPulse 웹 UI는 "데이터가 풍부한 분석 도구의 외형"을 갖췄지만, 그 외형이 차용된 패턴(Strava 활동 리스트 + Garmin Connect 카드 + Intervals 차트)이고, RunPulse만이 가진 자산(4-source 통합, 32개 자체 메트릭의 계산 투명성, 시간축 내러티브, 결정 지원) 중 어느 것도 UI의 일급 시민으로 표현되지 않았다. 더 결정적인 것은, 데이터 접근 계층이 UI에 섞여 있어서 "UI만 갈아엎는다"는 시도 자체가 구조적으로 불가능하다는 사실이다.

## 3. 데이터 레이어 ↔ 비전 적합도 진단

### 3.1 종합 점수 — **8.5/10**

| 비전 요소 | 점수 | 비고 |
|---|---|---|
| 원칙 1: 데이터 통합·소유권 | 9/10 | 핵심 설계 원칙이 비전과 일치 (P1~P4, ADR-002) |
| 원칙 2: 투명한 분석 | 8/10 | 사전·그래프 만점. 메트릭 분해 JSON 스키마 표준화 필요 |
| 원칙 3: 맥락 있는 안내 | 8/10 | AI 컨텍스트 풀세트 가능. 사용자 입력 모델 미설계 |
| 정체성 경계 | 9/10 | 러너 프로필 명시 모델 부재 |
| 확장성 | 10/10 | 새 소스·새 스포츠·ML·알고리즘 버전업 무한 수용 |

### 3.2 핵심 메시지

**메시지 1 — "데이터는 충분하다. UI가 부족하다."**
UI 점수 3/10과 데이터 점수 8.5/10의 5.5점 갭이 RunPulse의 현 상태를 정확히 설명한다. 비전 미달성의 원인은 **데이터 부재가 아니라 UI 표현 능력 부재**다. 좋은 소식이다 — 리뉴얼이 데이터 재설계까지 동반할 필요가 없다.

**메시지 2 — "데이터 레이어가 너무 풍부해서 UI가 압도된다."**
32 calculator + 13 시맨틱 그룹 + 4 provider + 6 카테고리 + 다중 scope. 이 풍부함을 카드 누적형 대시보드에 담으면 정보 폭주가 된다. 새 UI는 이 풍부함을 **층화(layering)와 여행 흐름(journey)**으로 풀어야 한다.

**메시지 3 — "리뉴얼과 함께 풀어야 할 데이터 레이어 확장 5건이 있다."**

| 번호 | 항목 | 비고 |
|---|---|---|
| D1 | 합성 메트릭 `json_value` 분해 스키마 표준화 (`{components: [{label, value, weight, raw}]}`) | 원칙 2 (투명성) 강화 |
| D2 | 활동 그룹 ID 모델 명시화 (auto_group 결과를 그룹 마스터 테이블로) | 원칙 1 (통합) 강화 |
| D3 | `user_inputs` 테이블 신설 (RPE/통증/노트), `ai_feedback` 테이블 신설 | 비전 5.3, 7장 KPI |
| D4 | `athlete_profile_snapshots` 테이블 신설 (러너 프로필 마스터, 다중 프로그램 입력) | 비전 A.2 |
| D5 | `src/services/` 서비스 레이어 신설 (BACKLOG `AUDIT-SERVICE-LAYER` 해결) | 모든 리뉴얼의 전제조건 |

**D5는 다른 모든 UI 리뉴얼의 전제조건**이다. 서비스 레이어 없이는 새 UI도 또다시 "raw SQL을 다른 모양의 HTML로 옮기는 작업"이 된다.

## 4. Phase 7 6~9장 재독 — 분기점 추천 재검토

### 4.1 6장 (단계별 실행 로드맵) → 마이그레이션 단계 순서 조정

6장이 1단계 묶음으로 정의한 것: **사용자 입력 인프라 + AI 코치 MVP(Context Builder + LLM API) + 비러닝 활동 + PWA + 홈 대시보드 개편**.

이는 분기점 D에서 처음 추천한 "Library 먼저 → Today → Story → Coach → Plan" 순서와 **불일치**한다.

**재검토 결과**: 6장의 묶음이 더 합리적이다. 사용자 입력과 AI 코치 MVP는 Today 영역과 함께 묶여야 가치 발현이 즉시 보이고, Library를 먼저 만든다고 사용자가 즉각 가치를 느끼지 않는다.

**수정된 단계 순서**:
1. **1단계 (Phase 7a 매핑)**: Today + 사용자 입력 + Coach MVP + 메트릭 드릴다운 인프라
2. **2단계 (Phase 7b 매핑)**: Library 전면화 + Story(내러티브 인사이트) + 적응형 프로그램 기반
3. **3단계 (Phase 7c 매핑)**: Plan 다중 프로그램 + ML 개인화
4. **4단계 (Phase 7d 매핑)**: 신규 데이터 소스 확장 + Training Balance Radar 완성

**중요**: 메트릭 드릴다운은 1단계에 **인프라 형태로 포함**된다 — 전용 Library 화면이 2단계로 미뤄지더라도, "메트릭에서 계산식·근거로 드릴다운하는 컴포넌트 패턴"은 1단계에 박혀야 한다. Today와 Coach에서도 이 컴포넌트를 사용하기 때문이다.

### 4.2 7장 (성공 측정) → 컴포넌트 카탈로그 1번 항목 강제

7장의 5개 정량 지표 중 UI에 강한 요구를 거는 것은 다음 둘이다.

- **(2-2) AI 답변에 평균 2개 이상 근거 인용** — 모든 AI 응답 컴포넌트는 **근거 인용 슬롯**을 가져야 함
- **(2-3) 사용자 입력 도달 60% 이상** — 입력 UI가 **첫 화면에서 한 손가락 거리**에 있어야 함
- **(5-2) AI 답변의 근거 추적 가능성** — 각 근거 인용은 **원천 데이터로 점프 가능**해야 함

→ **컴포넌트 카탈로그 1번 항목: `<EvidenceQuote>` 컴포넌트.** AI 응답 안에서 메트릭/차트/활동을 인용할 때 클릭 가능한 칩 형태로 렌더. 클릭하면 우측 패널이나 모달로 원천 데이터 점프.

→ **IA의 모든 핵심 영역에 빠른 입력 진입점**: Today, Coach, Library, Activity 상세 모두에 RPE/통증 입력 단축키.

### 4.3 8장 (차별화 전략) → 분기점 B (기술 스택) 제약 보강

8장의 "클라우드 종속이 아니다", "로컬 퍼스트", "데이터는 사용자 소유" 원칙이 분기점 B의 SvelteKit/Next.js + 별도 API 분리 모델과 약간의 긴장을 만든다.

**해결**: B2 추천을 유지하되 다음 제약을 명시한다.

- **단일 프로세스 배포 가능성** — SvelteKit/Next.js를 **standalone build**로 만들어 Flask와 같은 프로세스에서 정적 자산으로 서빙. 별도 Node 서버 불필요.
- **빌드 산출물의 단순성** — `python serve.py` 한 줄로 풀스택이 뜨는 정체성 유지.
- **Tauri/Electron으로의 데스크탑 패키징 가능성**을 미래 옵션으로 남김 — 데이터 소유권 정체성의 궁극적 표현.

또한 8장의 결정적 문장 *"PMC만 보여주는 것이 아니라, PMC를 구성하는 모든 활동의 모든 메트릭이 한 번의 클릭으로 도달 가능"* 은 **모든 차트에 드릴다운 인터랙션이 의무**라는 디자인 원칙으로 박힌다.

### 4.4 9장 (5년 후 비전) → IA의 정체성 표현 요구

9장의 "이 앱 하나로 충분한가? Yes"가 진실이 되려면, 다른 4개 탭의 핵심 정보가 RunPulse에 통합되어 있다는 사실을 사용자가 **명시적으로 느껴야** 한다.

→ **Library 영역의 핵심 화면**: "어느 메트릭이 어느 provider에서 왔고, RunPulse가 어떻게 합성했는가"를 한 페이지에 보여주는 화면. 시맨틱 그룹 13개 × provider 4개 매트릭스가 일급 시민으로 시각화.

이 화면 자체가 RunPulse 정체성의 표현물이 된다. Strava·Garmin·Intervals·Runalyze가 가지 못한 자리를 차지한다는 메시지를 시각적으로 박는다.

## 5. 분기점 최종 결정

### 5.1 분기점 A — 정보 구조 (IA)

**결정: A2 — 사용자 의도 중심 IA**

5+1 영역:

1. **Today (오늘)** — 일일 결정 지원. UTRS·CIRS·오늘 권장·빠른 입력·AI 브리핑이 한 화면. *"오늘 무엇을 할까"에 답하는 단일 화면.*
2. **Story (이야기)** — 시간축 내러티브. "지난 N주의 이야기" 형태로 데이터를 스토리텔링. 내러티브 인사이트가 일급 시민. *"내 상태는 어떻게 변하고 있나"에 답함.*
3. **Library (데이터·메트릭)** — 활동·메트릭·웰니스의 전수 조사 가능 영역. 메트릭 드릴다운, provider 비교, 원천 데이터 추적. *"왜 이 숫자가 이런가"에 답함.*
4. **Plan (계획)** — 다중 경로 프로그램 생성·비교·실행·사후 분석. 적응형 실행이 일급. *"다음 레이스를 위해 무엇을 할 계획인가"에 답함.*
5. **Coach (코치)** — AI 대화. Persistent Athlete Context 3계층 기반. Diagnostician/Analyst/Strategist/Guardian/Historian 5역할. *"내 코치와 대화"에 답함.*
6. **Data (운영)** — 동기화·소스 연결·내 데이터 export·설정. *운영 영역, 일급 시민 아님.*

URL 호환: `/dashboard → /today`, `/report → /story`, `/activities → /library/activities`, `/training → /plan`, `/ai-coach → /coach`, `/sync, /settings → /data/*` 리다이렉트.

### 5.2 분기점 B — 기술 스택

**결정: B2 변형 — SvelteKit + Tailwind + Flask API + 단일 프로세스 배포**

| 항목 | 결정 |
|---|---|
| 프론트엔드 | **SvelteKit** (1차 추천) 또는 Next.js (2차 추천) |
| 스타일링 | **Tailwind CSS + 디자인 토큰** |
| 컴포넌트 라이브러리 | **shadcn-svelte** (또는 Skeleton UI / Bits UI) |
| 차트 | **Visx 또는 ECharts** (Story 영역은 D3 커스텀도 검토) |
| 백엔드 | **Flask 유지 + API 모드 전환** (템플릿 렌더링 제거, JSON only) |
| 배포 | **단일 프로세스** — SvelteKit standalone build를 Flask 정적 자산으로 서빙 |
| PWA | **service worker + manifest + 오프라인 캐시 전략 풀세트** |
| 미래 옵션 | **Tauri 데스크탑 패키징** — 데이터 소유권 정체성의 궁극 표현 |

선택 이유: 데이터 8.5/10의 풍부함을 인터랙티브하게 표현하려면 풀 SPA 능력이 필요. SvelteKit이 RunPulse의 로컬 퍼스트 정체성·1인 개발 환경·번들 크기에 가장 정합. Flask는 인증·동기화·bg_sync 자산이 풍부해 그대로 API 서버로 활용.

**대안 시나리오 (B4)**: 사용자가 1인 개발 학습 곡선 부담을 크게 느끼면 HTMX-first + 차트만 Svelte 컴포넌트 islands. 다만 두 패러다임 공존의 장기 비용 인지 필요.

### 5.3 분기점 C — 디자인 언어

**결정: C2 + 부분 C3 — Quiet Data 미니멀리즘 + Story 영역 에디토리얼**

- **베이스 디자인 언어**: Quiet Data 미니멀리즘. 데이터의 시각적 잉크가 가장 강하고, 컨테이너는 거의 보이지 않음. Tufte data-ink ratio 원칙. 의미 있는 컬러만 사용 (등급·provider·강조).
- **타이포그래피**: Inter Variable (본문) + JetBrains Mono (숫자). 정보 위계의 주된 도구.
- **컬러**: 다크 모드 기본, 라이트 모드 동시 지원. 등급 색상 5단계 (excellent/good/moderate/poor/danger). Provider 컬러 4종.
- **모션**: 절제. 데이터 변경 시 부드러운 트랜지션, UI 장식적 모션 없음.
- **Story 영역 예외**: 에디토리얼 디자인 가미. 큰 타이포그래피, 여백, 차트가 문장 사이 인라인 등장.
- **레퍼런스**: Linear, Stripe Dashboard, Vercel Analytics, Observable Notebook, Granola.
- **글래스모피즘 폐기**: 현 다크 글래스모피즘은 정보 밀도가 높은 도구 UI에 부적합 — 폐기.

## 6. 설계 원칙 8개 — 모든 화면·컴포넌트가 따라야 할 규범

후속 설계 문서(`01-design-principles.md`)에서 상세화될 8개 원칙을 여기서 미리 박는다.

1. **Evidence-First (근거 우선)** — 모든 결론·권장·점수는 근거 인용 슬롯을 동반한다. 근거는 클릭 가능하고 원천 데이터로 점프한다. *(비전 원칙 3, 7장 KPI)*
2. **Drillable Everything (어디든 드릴다운)** — 모든 메트릭과 차트는 한 번의 인터랙션 안에서 계산 분해·원천 데이터까지 도달 가능하다. *(비전 원칙 2, 8장 명시 요구)*
3. **Provider Transparency (출처 투명성)** — 메트릭 값 옆에는 항상 provider가 표시되거나 한 번의 인터랙션 안에서 확인 가능하다. 동일 메트릭의 타 provider 값과 비교 가능하다. *(비전 원칙 1, 9장 정체성 요구)*
4. **Intent-Centered IA (의도 중심 IA)** — 정보 구조는 기능 분류가 아니라 사용자 의도로 조직된다. 매 진입에 사용자는 자기 의도와 매핑되는 영역으로 즉시 간다. *(비전 페르소나)*
5. **Quiet Data (조용한 UI, 시끄러운 데이터)** — UI 장식은 절제하고 데이터의 시각적 잉크가 가장 강하다. 정보 밀도와 위계는 타이포그래피·여백·분할선으로 만든다. *(분기점 C 결정)*
6. **One Finger Reach for Input (입력은 한 손가락 거리)** — RPE·통증·노트 입력은 모든 핵심 영역에서 한 손가락 거리에 있다. 입력 마찰을 최소화한다. *(7장 KPI: 사용자 입력 도달 60%)*
7. **State-Bound Plan (상태에 묶인 계획)** — 훈련 계획은 시간이 아니라 러너의 상태에 묶인다. 모든 계획 UI는 적응 가능성을 시각화한다. *(비전 A.6)*
8. **Local-First Identity (로컬 퍼스트 정체성)** — UI 어디서도 클라우드 종속을 느끼게 하지 않는다. 데이터 소유권이 표현된다 (export·snapshot·원본 보존이 일급). *(8장 차별화)*

## 7. 컴포넌트 카탈로그 1차 초안 — 7개 핵심 컴포넌트

후속 설계 문서(`04-component-catalog.md`)에서 상세화될 핵심 컴포넌트.

1. **`<EvidenceQuote>`** — AI 응답·내러티브·권장 안에서 메트릭/차트/활동을 인용. 클릭 가능 칩으로 렌더, 클릭 시 우측 패널이나 모달로 원천 점프. *(원칙 1, 7장 KPI 직접 매핑)*
2. **`<MetricCell>`** — 메트릭 값 + provider 표식 + 등급 배지 + 호버 시 정의 + 클릭 시 드릴다운. 모든 화면에서 메트릭을 표시하는 기본 단위. *(원칙 2, 3)*
3. **`<MetricBreakdown>`** — 합성 메트릭(UTRS, CIRS, RRI 등)의 계산 분해 시각화. `metric_store.json_value`의 표준 분해 스키마(D1)를 입력으로 받아 components를 가중치 시각화. *(원칙 2)*
4. **`<ProviderComparison>`** — 동일 시맨틱 그룹의 다중 provider 값을 병렬 표시. 시맨틱 그룹 13개 × provider 4개 매트릭스의 셀 단위 컴포넌트. *(원칙 3, 9장 정체성)*
5. **`<QuickInput>`** — RPE·통증·노트 빠른 입력. 모든 영역에서 한 손가락 거리에 배치. 키보드 단축키 지원. *(원칙 6, 7장 KPI)*
6. **`<RecommendationCard>`** — 오늘의 권장 / Coach 응답. 결론 + 근거 인용(`<EvidenceQuote>` 2개 이상 의무) + 액션 + thumbs up/down 피드백. *(원칙 1, 7장 KPI)*
7. **`<TimelineNarrative>`** — Story 영역의 핵심 컴포넌트. 시간축에 데이터·차트·인용을 인라인 배치. 에디토리얼 디자인. *(비전 5.2 내러티브 일급 시민화)*

## 8. KPI 매핑 — 7장 정량 지표 ↔ 설계 산출물

7장이 정의한 5개 정량 지표 각각이 어떤 설계 산출물로 달성되는지 매핑한다.

| KPI | 목표 수치 | 책임 산출물 |
|---|---|---|
| 메트릭 매핑 일관성 | 95% 이상, `_unmapped` 5% 미만 | 데이터 레이어 (기존) + Library의 매핑 가시화 |
| 활동당 메트릭 수 | 최소 50개 | 데이터 레이어 (기존) + Library 활동 상세 화면 |
| AI 답변 근거 인용 | 평균 2개 이상 | `<RecommendationCard>` + `<EvidenceQuote>` 의무 슬롯 |
| 사용자 입력 도달 | 60% 이상 | `<QuickInput>` + 한 손가락 거리 IA 배치 |
| 예측 정확도 (레이스) | ±3% 오차 | 데이터 레이어 (DARP) + Plan 사후 분석 화면 |
| 부상 경고 적중률 | 60% 이상 | 데이터 레이어 (CIRS) + Today의 Guardian 알림 |
| 4탭 통합 | 다른 앱 안 봐도 됨 | `<ProviderComparison>` + Library 시맨틱 그룹 매트릭스 |
| 근거 추적성 | 모든 결론에서 가능 | `<EvidenceQuote>` 의 점프 인터랙션 |

이 매핑은 **설계 완료 검증 체크리스트**로 사용된다. 각 KPI가 달성 가능한 산출물이 1개 이상 매핑되어야 설계 완료로 간주한다.
