# DESIGN-PLAN-METHODS — 훈련 방식 선택 (목표 거리별 다중 방식)

상태: **초안, 사용자 승인 대기** (2026-11-20). 승인 전 구현 금지. 결정 번호는 승인 후 ADR-060 으로 기록.

## 1. 목표와 범위

- 계획 수립은 **규칙 엔진이 담당**하고 AI 는 보조다. AI 가 계획을 직접 짜지 않는다(AI 초안은 게이트 거부가 잦음: 브라우저 스모크 2회 연속 거부).
- 목표 거리(10K·하프·풀)마다 **여러 훈련 방식**을 두고, 사용자가 목표별로 고른다.
- 선택 UI 에는 방식마다 **장점·단점·추천 대상**과 이 사용자에 대한 **추천안**을 보인다.
- 건달프식(`data/2026_marathon_plan/50_REFERENCES/GUNDALF_*.md`)을 방식으로 포함한다.
- 비범위: 노르웨이식 이중 역치(하루 2회 필요, 사용자 보류), 갤로웨이·리디아드(후속 선택).

## 2. 현재 구조(변경 지점)

| 계층 | 파일 | 역할 |
|------|------|------|
| 주기화 | `src/training/periodization.py` | 대회 역산, 테이퍼·base/build/peak, RAMP 10%, 3:1 회복주 상수 |
| 주간 생성 | `planner.py` → `planner_v2.py`, `planner_v2_long.py` | 80/20, Q-day, 하드-이지, MP 세션, 롱런 예산 |
| 환경 | `planner_config.py`, `plan_structure.py` | 사용자 가능 요일·피트니스 조회 |
| 규칙 버전 | `goals.plan_rules_version`, `plan_replans.rules_version`(anchor 별) | v1/v2 분기 |
| AI | `services/plan_draft.py` | 4주 ±15% 정제, 게이트 통과분만 저장 |

방식은 **규칙 버전과 직교하는 새 축**이다(rules_version = 알고리즘 세대, method = 훈련 철학).

## 3. 아키텍처

### 3.1 방식 레지스트리 `src/training/methods/`

방식 하나 = 불변 데이터클래스 `PlanMethod`(순수, DB 무접근).

- `id`(예 `balanced`, `gundalf_sub3`), `distances`(적용 목표 거리 집합), `label`·`summary`
- `pros`·`cons`·`target_runners`(UI 문구, 각 2~3줄), `sources`(근거, 출처 등급 포함)
- `periodization`: 기존 상수 오버라이드(`ramp`, `taper_factors`, `phase_split`, `long_step`, `recovery_factor`, `peak_km_range`)
- `weekly_template`: 주 러닝 일수별 요일 슬롯 → 세션 종류(easy·long·quality 종류·benchmark·rest) 매핑
- `session_specs`: 종류별 거리·강도 규칙(페이스는 기존 VDOT/eFTP 존에서 산출, 방식은 비율·세트만 지정)
- `requirements`: 최소 주 일수, 권장 주간 km·준비 기간(추천·경고 판단용)

`balanced` 는 **현재 규칙을 그대로 옮긴 기본 방식**이다. 이 방식에서 생성 결과가 현행과 **바이트 단위로 동일**해야 한다(회귀 기준, §7).

### 3.2 파이프라인 주입

`generate_weekly_plan(conn, goal, …)` 가 `get_method(conn, goal_id, week_start)` 로 방식을 얻어 주기화·주간 생성기에 인자로 전달한다. 모듈 상수를 직접 읽던 곳은 `method.periodization` 값을 받도록 바꾼다(기본값은 기존 상수 → `balanced` 는 무변경). 특수 템플릿(건달프의 기준 러닝 등)은 `planner_v2` 후처리 단계에서 `weekly_template` 로 슬롯을 덮어쓴다.

### 3.3 저장(스키마 v51)

- `goals.plan_method TEXT NOT NULL DEFAULT 'balanced'`
- `plan_replans.plan_method TEXT` — anchor 별 방식(v35 의 `rules_version` 과 같은 방식, `effective_method(conn, goal_id, week_start)`)
- 기존 목표·기존 replan 은 `balanced` 로 간주 → 생성 결과 변화 없음.

### 3.4 변경 경로

- 목표 **생성 시** 방식 선택(미선택 = 추천안).
- 진행 중 목표의 방식 변경은 **재계획 경로(`plan_replan_service`) 전용**, 되돌리기(undo) 지원. 과거 주는 건드리지 않는다(anchor 이후만 새 방식, ADR-035 부록 R).
- 방식·목표 불일치(예: 주 3일인데 건달프 풀)는 **경고만**, 선택은 막지 않는다.

### 3.5 AI 의 역할 (적극 활용 — 사용자 결정 2026-11-20)

RunPulse 의 장기 데이터(주간 볼륨 이력, 일관성, 대회 이력, VDOT·eFTP 추세, 과거 블록 반응, 부상·컨디션)를 AI 가 직접 읽고 러너별 최적 방식을 판단한다.

1. **방식 추천(핵심)**: 규칙은 *후보 거르기*(실행 가능 요일 수, 거리 적용 여부, 부상 이력 하드 가드)만 하고, 후보 중 **순위·선택·이유는 AI** 가 장기 데이터로 판단한다. 고정 수치 임계값으로 추천을 결정하지 않는다.
2. **파라미터 개인화**: 선택된 방식의 허용 범위 안에서 AI 가 주간 거리·롱런·강도 배치를 조정(게이트 통과 시만 반영).
3. **게이트**: AI 출력은 후보 목록 안의 id 만 허용, 범위 밖·파싱 실패·큐 불가 시 규칙 폴백(결정적 기본 추천). AI 는 방식 템플릿 자체를 바꾸지 않는다.
4. 기반: ADR-059 계층(`ai_outputs` 캐시·동의 게이트)과 claude_queue 재사용.

## 5. 추천 (AI 판단 + 규칙 가드)

**규칙(하드 가드, 결정적)**: 후보 = 해당 거리에 적용되는 방식 중 (a) 선택 가능 러닝 요일 수 충족, (b) 최근 부상 이력이 있으면 고강도 방식에 경고 플래그. 후보에서 빠지는 것은 물리적으로 불가능한 경우뿐이고, 나머지 부적합은 **경고**로 남겨 선택은 막지 않는다.

**AI 판단**: 입력 = 후보 목록(각 방식의 요구 조건·특성) + 러너 장기 요약(최근 12~24주 주간 km·러닝 일수, 일관성, 대회 이력·PB, VDOT·eFTP 추세, 과거 블록 이행·반응, 부상·웰니스, 남은 주, 목표 시간). 출력 JSON = `{recommended, ranking[], reasons{id: 한 줄}, warnings{id: 한 줄}}`.

**게이트**: id 가 후보 안, ranking 은 후보 부분집합, 이유 길이 상한. 실패·큐 불가·동의 없음 → 규칙 폴백(`balanced` 우선, 요일 수 3 이하면 `first_run3` 존재 시). 결과는 `ai_outputs` 에 캐시(입력 해시 키). 추천은 항상 1개를 상단, 나머지는 접는다.

## 6. UI

- 목표 생성 화면에 "훈련 방식" 섹션: 추천 카드 1개(이유 1줄 포함) + "다른 방식 보기" 접기.
- 방식 카드: 이름, 한 줄 요약, 장점·단점·추천 대상, 이 사용자에게의 경고(있을 때).
- 계획 화면: 현재 방식 배지 + "방식 변경" → 재계획 시트(되돌리기 포함).
- 브라우저에서 실제 확인(375px 포함).

## 7. 검증

- `balanced` 회귀: 대표 목표 시나리오 N개에서 기존 출력과 동일(스냅샷 테스트).
- 방식별 단위 테스트: 요일 슬롯·주간 km·롱런 상한·테이퍼·런 일수 제약, 건달프 기준 러닝 페이스 갱신(성공/실패).
- 방식별 `plan_backtest` 실행(안정성: 주간 증가율 ≤ 방식 RAMP, 회복주 존재, 대회 주 감량).
- `plan_draft` 게이트가 방식별 계획에서도 동작.
- 마이그레이션 테스트(v50→v51, 기존 데이터 `balanced`).
- 완료 시 `pytest`, `check_docs.py`, `gen_files_index.py`.

## 8. 구현 단계

1. 스키마 v51 + `methods/` 레지스트리 + `balanced` 이관(무변경 회귀).
2. 계획 파이프라인 파라미터 주입, 방식 선택 API(목록·설정), 재계획 경로 연결(과거 주 유지, anchor 이후만).
3. **AI 추천**(후보 가드 + 장기 데이터 요약 + 게이트 + 폴백) — 방식이 `balanced` 1개뿐이어도 골격·테스트 가능.
4. 방식 추가(분량 순): `gundalf_sub3` → `gundalf_10k_base` → 나머지(원전 확인 후).
5. UI(목표 생성·계획 화면·재계획 시트).
6. AI 파라미터 개인화.

각 단계는 결과 보고 후 사용자 확인 뒤 진행.

## 10. 결정 사항 (2026-11-20 사용자 확정)

1. 추천은 고정 임계값이 아니라 **AI 가 장기 데이터로 판단**(§5).
2. 하프 건달프(`gundalf_hmp`)는 출처가 없으므로 **제외**.
3. 방식 변경 시 과거 주 유지, **anchor 이후만** 새 방식 적용.
4. AI 를 적극 활용(§3.5).
