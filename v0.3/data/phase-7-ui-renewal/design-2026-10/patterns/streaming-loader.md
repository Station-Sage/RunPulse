- 작성일 2026-11-11 · 상태: 보수안 채택·구현 완료(사용자 재검토 대상) · 문구 TXT-1 확정

## 1. 플랜 상세 로더 — 무엇을 기다리고 무엇을 흘려보낼까

전: `coach/plan/[id]/+page.ts` 가 5개 요청(플랜·오늘 조정·적응 지표·재계획 상태·주차표)을 `Promise.all` 로 모두 기다렸다.
가장 느린 하나가 화면 전체를 막고, 콜드 로드에서는 부트 스플래시(S-05)가 그만큼 오래 남았다.

후보: (A) 아무것도 기다리지 않고 전부 약속으로 넘김 — 콜드 로드에도 바로 스켈레톤이 보이지만, 뒤로 가기 스크롤 복원이
비어 있는 화면에서 일어나고, 행 조작 뒤 `invalidateAll` 마다 화면 전체가 스켈레톤으로 깜빡인다. 플랜 404·오류 분기도
화면 안 `{#await}` 로 옮겨야 한다. (B) 머리·이번 주 목록에 필요한 **플랜만 기다리고** 나머지 넷은 약속으로 넘김.
(C) 플랜+오늘 조정을 기다림(조정 카드가 목록 위에 끼어드는 흔들림 방지).

채택: **(B)**. 첫 화면에 필요한 데이터·오류 분기·스크롤 복원·`+error` 동작이 전과 같다. 오늘 조정 카드는 조정이 있는 날만
보이고, 합성 서버에서는 다섯 요청이 모두 7~17ms 로 비슷해 (C) 의 이득을 확인할 수 없었다(실계정 응답 시간은 재지 않음 —
오늘 조정이 실제로 느려 카드가 늦게 끼어드는 흔들림이 보이면 (C) 로 옮기는 것이 한 줄 변경).
SPA(`ssr=false`, adapter-static fallback)라 SvelteKit 은 반환한 약속을 직렬화하지 않고 그대로 넘긴다. 넘기는 약속은
거부되지 않는다(`toResult`·`catch`) — 처리 안 된 거부도 `+error` 전환도 없다. 규칙은 `$lib/planDetailLoad.ts`(API 주입,
단위 테스트), 화면 상태 전환은 `$lib/streamed.ts`: 같은 플랜을 다시 읽을 때(invalidate)는 새 값이 올 때까지 이전 값을 유지해
깜빡이지 않고, 다른 플랜 id 로 바뀌면 바로 자리 표시로 돌아가며, 늦게 끝난 옛 약속은 무시한다.

자리 표시: 주차표·적응 상태 자리에만 스켈레톤(`plan-weeks-skeleton`·`plan-adaptation-skeleton`, `aria-busy`). 조정 카드와
재계획 줄은 조건부라 자리를 잡지 않는다(없는 날이 대부분이라 빈 자리가 접히는 흔들림이 더 잦음). 레이아웃의 이동 대기 스켈레톤
(`navSkeleton`, S4-86)은 그대로 두어 "플랜을 기다리는 구간"을 맡는다. 콜드 로드는 앱 번들·레이아웃 로더가 끝나야 첫 화면이
그려지므로 스플래시 → (플랜 도착) 머리+목록+스켈레톤 순서가 된다. 스플래시를 더 줄이려면 (A) 가 필요 — 하지 않음.

## 2. 미래 시작 플랜의 재계획 기준일

S4-86 발견: 첫 주가 미래(11/23)인 플랜에서 다시 맞추기 미리보기가 그 앞 주(11/16)에 47.8km 주를 붙였다. 원인은
`plan_replan_service` 의 기준일이 항상 `next_monday(today)` 였던 것. 그 주는 계획 범위 밖이라 `week_target` 이 None 이 되고
`generate_weekly_plan` 이 CTL 기반 폴백 거리(주기화 아님)로 한 주를 만들어 `replace_range` 로 써 넣었다(그 주의 다른 행도 교체 대상).
"첫 주 34km — 최근 4주 평균 그대로" 문구는 계획 첫 주(11/23) 기준이라 맞았고, 표만 틀렸다.

결정: 재계획 기준일 = `max(다음 월요일, 계획 시작 월요일)`(`replan_anchor`). preview·apply 의 `expect_anchor` 확인·진입 규칙
RACE_NEAR 가 같은 함수를 쓴다. 되돌리기 기한은 기준일 전날(계획 시작 전날)까지로 자연히 따라온다. 주기화 규칙(`fold`)은
기준일이 계획 시작 이전이면 0주차로 접으므로 일정 계산은 그대로다. 계획 앞 주는 다시 짜지도 지우지도 않는다.
프런트 요약은 전에 없던 첫 주(before 없음)를 "비슷한 거리"로 말하던 비교 오류만 고쳤다(서버 수정 뒤에는 생기지 않는 경우).

## 3. 함께 고친 것 — 재계획 미리보기 'database is locked'

합성 서버 스모크 중 미리보기가 1회 500(`sqlite3.OperationalError: database is locked`). SAVEPOINT(지연 트랜잭션)로 읽은 뒤
INSERT 로 쓰기 잠금을 올리는 사이 다른 연결이 커밋하면 SQLite 는 busy 대기 없이 바로 실패한다(WAL 스냅샷 충돌).
재계획 실행은 이제 연결이 트랜잭션 밖이면 `BEGIN IMMEDIATE` 로 쓰기 잠금을 먼저 잡는다(다른 쓰기는 busy timeout 동안 대기).
미리보기는 끝에 되돌린다. 재현 테스트: `test_preview_holds_write_lock_so_concurrent_commit_cannot_break_it`.
