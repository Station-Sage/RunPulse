1. **실행 가능성**: 1주차 40.5km는 v1(43.3km)보다 조금 작은 정도다. 하지만 6km 미만으로 쪼개진 세션이 없고 휴식일이 있어서 실제 패턴(주 4일, 7~10km)과 맞는다. 피크 주 53.7km는 직전 16주 최대(63.1km, 8/10 주) 아래다.
2. **롱런 진행이 실제 최장에서 출발한다**: 18.2 → 20.2 → 22.2 → 24.0km로 주당 +2km씩 늘어난다(F6 허용 범위 안). v1은 27.2 → 21.1 → 29.9 → 32.0km로 오르내린다.

4. **테이퍼**: 풀 2주 감량 + D−14 롱런 24.0km. v1은 3주 감량이고, 마지막 롱런이 D−14에 20.8km다.

## 3. 적용 방식 설계(사용자 승인 재계획)

### 3.1 X1 — 규칙 버전을 anchor 단위로
- 스키마 v35: `plan_replans.rules_version INTEGER NULL`. NULL이면 goal의 버전을 따른다(기존 행과 같은 동작).
- `goals.effective_rules_version(conn, goal, week_start)`: `week_start` 이하의 applied anchor 중 가장 늦은 것의 `rules_version`을 쓰고, 없으면 `goals.plan_rules_version`을 쓴다. 지금 버전을 읽는 네 곳(`planner.py`의 v2 분기, `planner_schedule._rules_version`·`week_cap_km`·`plan_start_source`, `weekly_adapt_service`, `plan_readiness`)을 이 함수로 바꾼다.
- `schedule_for_goal`: 기본 일정(접두)은 goal 버전으로 만들고, 꼬리는 `_build(..., rv=anchor.rules_version or goal rv)`로 만든다. `plan_anchor.Anchor`에 `rules_version` 필드를 추가한다.
- 되돌리기: anchor를 `undone`으로 바꾸면 버전도 자동으로 원래대로 돌아온다. 따로 처리할 것이 없다.
- 이렇게 하면 D-U16-2(목표별 고정)는 "목표별 기본값 + 기록된 명시적 전환"으로 바뀐다. 전환할 때마다 `plan_replans`에 기록이 남으므로 "몰래 규칙이 바뀌지 않게"라는 원래 의도는 유지된다.

### 3.2 흐름
1. `GET /coach/plan/replan/preview?rules_version=2`. v1 목표에서만 허용한다. `PLAN_RULES_V2_ENABLED`와는 별도로 서버 상수 `REPLAN_UPGRADE_ENABLED`로 연다.
2. 미리보기 응답의 주별 전/후 비교에 `run_days`, `rest_days`, `hard_count`, `mp_km`, `long_km`, `min_session_km`를 추가한다. 지금은 `planned_km`, `long_km`만 있다. 이번 판단 근거가 되는 구조 변화(휴식·MP·세션 길이)는 거리만으로는 보이지 않는다.
3. `POST /coach/plan/replan`의 본문에 `rules_version`을 넣는다. 미리보기와 같은 값이 아니면 409 `CONFLICT`를 돌려준다(`expect_anchor`와 같은 방식).
4. 되돌리기는 지금 규칙 그대로다(마지막 1건, anchor 전까지, 새 행에 이력이 없을 때만).
5. anchor 이후에 v1로 돌아가려면 `rules_version=1`로 다시 재계획한다. 다음 월요일부터 v1 꼬리가 만들어지고, 이미 v2로 지난 주는 그대로 남는다.

### 3.3 자동 이행을 거부하는 이유
- 이 러너의 v2 결과는 처방이 바뀐다. 피크 롱런이 32km에서 24km로 줄고, 처음으로 MP 세션이 생긴다. 목표 기록에 대한 기대가 달라지는 변화이므로 사용자가 미리보기로 확인해야 한다.
- 계정이 하나뿐인 지금은 자동 이행의 이득(모든 v1 목표를 일괄 처리)이 없다.

## 7. 가정과 한계
- 시뮬레이션은 2026-10-10 운영 DB 사본 하나에서, 휴식 요일 두 가지 설정(mask 0, 월·수·금)으로만 돌렸다. X3·X4를 고친 뒤에는 결과(MP·시작 부하)가 달라지므로 E7 이후에 다시 측정해야 한다.
- "피크 롱런 24km면 3:19에 부족하다"는 일반 관행에 근거한 판단이다. 이 러너의 풀 기록은 1건뿐이라 백테스트로 최적성을 검증할 수 없다(D-U16-3).
- 실제 주간 km는 Garmin 소스만 합산했다. 서비스의 km4(`v_canonical_activities`, 28일 창)와 정의가 다르다.
