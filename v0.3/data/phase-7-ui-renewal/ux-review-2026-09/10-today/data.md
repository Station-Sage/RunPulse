## 발견

### [치명] F-DATA-01 PMC EMA 계수가 설계와 달라 CTL/ATL/TSB가 약 2배 빠르게 움직인다 — 모든 하위 지표의 바탕이 흔들린다
- 현상: 폼 차트의 CTL(체력)이 9/2 64.9 → 9/6 80.0 → 9/11 67.6으로 한 주 안에 ±15% 출렁인다. 3개월 동안 하루 최대 변동은 +11.7/−4.6이다. TSB는 −70~+24.8 범위이고, 91일 중 15일이 −30 미만(과부하 구간)이다. 롱런 다음 날(9/6 −56.7, 9/20 −44.0) TSB가 깊이 떨어졌다가 3일 만에 +15로 돌아오는 톱니 모양이 반복된다. 차트 ATL 선이 심하게 들쭉날쭉한 것(F-UI-08 e)도 같은 원인이다.
- 근거: `src/metrics/pmc.py:46-47` `atl_decay = 2.0/(ATL_DAYS+1)`, `ctl_decay = 2.0/(CTL_DAYS+1)`. 즉 α_ATL=0.25, α_CTL=0.0465다. 설계 원문 `v0.2/.ai/metrics.md:176-177`은 `CTL(n)=CTL(n-1)+(TRIMP−CTL(n-1))/42`, ATL은 `/7`이다. 실측 재현: ATL 7/1→7/4 무부하 구간 비율 0.750(=1−0.25), CTL 비율 0.953(=1−2/43). 부하 역산으로 9/20 롱런은 TRIMP 약 270이었다. 이 부하에 코드는 ATL +48.7, CTL +9.3을 올렸고, 표준 상수라면 ATL +27.9, CTL +4.8이다. `race_projection_service.py:62-63`도 같은 계수를 쓴다. 날짜마다 49일 창을 0부터 새로 계산하므로(`pmc.py:55`) 과거 값은 창 밖 부하를 버리는 절단 오차도 안고 있다(α=2/43에서 약 10% 과소, 추정).
- 왜 문제인가: CTL/ATL/TSB는 TrainingPeaks·Intervals.icu·Garmin과 비교하는 공통 언어다. 시정수가 절반이라 RunPulse의 "TSB −15"는 다른 앱의 "TSB −15"와 다른 양이다. 그런데 화면의 모든 기준선(레이스 최적 +5~+25, −10/−20 권고 임계, ACWR 0.8~1.3, CIRS의 ATL/80)은 표준 상수를 전제로 한 관행값이다. 그 결과 롱런 하루가 "과부하" 판정을 만들고, 3일 쉬면 "레이스 최적"이 된다. 정보 정확성 치명(틀린 수치가 오판을 유도)이다. P3(공식 투명성)과 U5에도 걸린다.
- 개선안:
  - 계수를 설계 원문(`1/N`, 또는 Coggan식 `1−e^(−1/N)`)으로 돌리고, `version`을 `pmc_v2`로 올려 전 기간을 재계산한다. 오늘 값만 고치지 말고 연속 재귀 시계열로 저장한다(창 절단 제거, 시작 시드는 첫 28일 평균).
  - 재계산 전후 비교표(최근 90일 TSB 범위, −30 미만 일수, 레이스 아침 TSB)를 DECISIONS에 기록하고, Library CTL 상세에 "v1→v2 변경" 마일스톤 1건을 남긴다.
  - Intervals.icu가 CTL/ATL을 제공하는 날에는 provider 비교(P3)로 차이를 노출해 회귀 검증에 쓴다.
  - `pmc.py`의 공식 문자열("ATL = 7일 EMA, α=1/7")을 분해 시트 공식 줄의 원천으로 삼는다(F-UX-01 ②와 연결).

### [치명] F-DATA-02 TRIMP(Banister) 계수 두 개가 뒤바뀌어 있다 — 쉬운 달리기 부하가 과대, 고강도는 과소

API `/library/activities/17414` → `trimp 97.3`, Garmin `training_load 110.2`.
- 왜 문제인가: TRIMP는 PMC·ACWR·LSI·연속훈련·레이스 투영의 유일한 부하원(`base.py:348-361`)이다. 저강도 볼륨이 부풀려지고 인터벌·템포의 자극이 상대적으로 작게 잡힌다. 그래서 "쉬운 날을 길게 뛰면 피로 누적 경고, 품질 세션은 부하가 작게"라는 방향 왜곡이 생긴다. 80/20 배분을 코칭하는 앱에서 강도 가중이 틀리면 권고의 전제가 무너진다.
- 개선안: 계수를 원문으로 고치고(성별은 프로필에서 받고 기본값은 남성, 분해 시트에 표시), F-DATA-01과 함께 한 번에 재계산한다. `tests/`에 원문 수치 고정 테스트(x=0.5 → 0.836/분, x=0.9 → 3.243/분)를 추가한다. Garmin training_load·HRSS와 활동별 상관을 provider 비교 탭에 노출해 이상치를 발견할 수 있게 한다.

## 잘된 점 (유지)
- 레이스 허브의 핵심 산식(예측·목표·격차·차이 %)은 화면, API, 역산이 초 단위까지 일치한다. 예측을 3경로(Garmin/기기 심박/자체)로 나눠 LTHR 차이의 영향(0.5%)까지 정량화한 것은 경쟁 앱에 없는 투명성이다.
- UTRS·CIRS 구성요소와 가중치가 `json_val`과 children으로 저장되어 산식 재현이 가능하다. 가중치 표시(F-UI-03)만 붙이면 분해의 질을 빠르게 올릴 수 있다.
- 개인 기온 모델(n=886), 자체 LTHR/HRR 존, 섀도 r4의 분산 기반 구간 등 레이스 결정에 필요한 재료는 이미 백엔드에 있다. 문제는 대부분 모델이 없어서가 아니라 연결과 해석에서 생긴다.
- ACWR은 만성 부하가 형성되기 전(CTL<10 또는 28일 이력 없음)에는 산출하지 않는다(`acwr.py`, P7-PRED-89). 공백기 복귀일에 가짜 "위험"이 뜨지 않는 좋은 방어다.
- 권고가 레이스 국면(빌드/테이퍼/레이스 주간/당일)을 인식해 문장을 바꾼다. 방향은 옳다.

## 최우선 개선 3개
1. **부하 모델 재기준화(F-DATA-01·02·03)**: TRIMP 계수를 원문대로, PMC α를 1/N으로 바로잡고 연속 재귀로 전 기간을 재계산한다(`pmc_v2`, `trimp v2`). 권고·링·UTRS에는 하루 동안 고정되는 "아침 폼"을 쓰고, 오늘 훈련 반영값은 잠정 표시로 분리한다. 원문 수치 고정 테스트를 추가한다.
2. **해석 SSOT와 권고 재설계(F-DATA-04·06·12)**: 등급 밴드·라벨을 `metric_registry` 한 곳에서 API로 내려주고 프론트 등급표 4벌을 제거한다. TSB 밴드는 관행(−30/−10/+5/+25)으로 통일한다. 권고는 CRS 게이트 + 계획 세션 + 체크인을 입력으로 "계획대로/하향 조정 + 근거 신호 2~3개"를 낸다. CIRS의 ACWR은 비대칭 위험식으로 바꾼다.
3. **레이스 결정 지원 정직화(F-DATA-05·07·08·09)**: 준수율을 거리·핵심 세션 가중으로 백엔드 단일 정의로 바꾸고, 대체된 롱런은 미이행으로 표시한다. "80% 범위"는 보정된 구간이나 "모델 범위"로 바꾸고 Daniels/Tanda 분해와 볼륨 민감도를 보여 준다. 목표 실현성 판정과 대안 목표를 제시한다. 레이스 아침 TSB는 실제 계획 기반 조건부 투영(TSB + 체력 변화율)으로 바꾼다.
