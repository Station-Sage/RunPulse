3. **같은 활동에 대한 RunPulse 자체 계산값이 소스 사본마다 다르다.** 9/27 러닝의 Relative Effort가 Garmin 사본에서는 302.3, Intervals 사본에서는 27.7로 11배 차이 난다. 매트릭스는 이 중 27.7을 보여 준다.
4. **마라톤 예측은 근거 데이터가 이미 있는데 분해 API가 비어 있다.** DB에는 범위 3:26:00~4:02:46, 신뢰도 0.36, 신호별 가중치(대회 .6/훈련 .2/심박 .2), 기준 대회 20주 전, Daniels 3:30:12 대 Tanda 3:51:04가 저장되어 있다. 그런데 화면은 `3:40:23`을 초 단위 정밀도로 핵심 지표 1번에 놓고, 분해는 `children: [], inputs: []`이다.
5. **부하·회복 신호 7개가 같은 원천에서 나오면서 판정은 서로 다르다.** 같은 시점에 ACWR 1.2는 "적정", TSB −14.7은 "피로 누적", CIRS 36.6은 "보통"으로 나오고, RTTI 130%는 레지스트리 기준 danger 경계인데 상태 표시가 없다. UTRS의 HRV 입력은 개인 기준선이 아니라 절대 범위(20~100ms)로 정규화한 주간 평균이라, 웰니스 화면에 보이는 야간 HRV 107ms와 연결되지 않는다.

## 발견

### [치명] F-DATA-01 CTL/ATL이 표준 τ(42/7일)보다 약 2배 빠르게 반응 — "42일 만성부하" 라벨과 실제 계산 불일치
- 현상: 3개월 CTL 차트(`metric-ctl-desktop.png`)가 톱니 모양으로 출렁인다. API의 일별 CTL을 보면 9/20 79.2 → 9/21 75.0 → 9/22 71.5 → 9/23 67.7로 **하루 3.5~4.2씩** 떨어진다. ATL은 9/20 123.2에서 9/21 92.4로 떨어졌고, TSB는 9/20 −44.0에서 9/23 +15.8로 3일 만에 60 가까이 움직였다.
- 근거: `src/metrics/pmc.py:62-63` `atl_decay = 2.0 / (self.ATL_DAYS + 1)`, `ctl_decay = 2.0 / (self.CTL_DAYS + 1)`. 이 식이면 α는 ATL 0.25, CTL 0.0465이고 실효 τ는 각각 4일, 21.5일이다. 표준 Banister/Coggan PMC(TrainingPeaks·Intervals.icu·Runalyze)는 α≈1/42, 1/7을 쓴다. 검산: 부하가 0인 날의 최대 하락폭은 α×값이다. 표준 CTL은 79.2/42 = 1.9가 한계인데 실측 하락은 4.2였다. ATL은 0.25×123.2 = **30.8**로 실측(123.2→92.4)과 정확히 일치한다(`/library/metrics/{ctl,atl}/trend?period=4w` 확인). 추가로 워밍업이 49일뿐이어서(`:54` `days=CTL_DAYS+7`) 매 계산을 0에서 시작한다. Intervals 자체 CTL과 비교하면 2026-05-08 Intervals 33.3 / RunPulse 48.8, 04-01 33.2 / 56.4였다(DB `metric_store` daily ctl, provider별 확인). 수준 차이(약 1.5배)는 정상상태에서 α와 무관하므로 부하 척도(TRIMP 대 Intervals load) 차이로 보이며, τ 차이는 변동폭 차이로 나타난다.
- 왜 문제인가: CTL을 "체력"으로 라벨링하고(`metricMeaning.ts:48`) 레이스 준비도(RRI의 ctl 입력)·마라톤 셰이프 판단에도 쓰는데, 롱런 하루와 휴식 사흘에 따라 "체력"이 ±10% 흔들린다. ATL(τ 4일)은 하루 롱런에 과민하게 반응해 TSB −44, CIRS 68.1(9/20)을 만들고, 이틀 쉬면 곧바로 TSB +15.8 "레이스 최적"을 띄운다. 러너가 Intervals/TrainingPeaks에서 익힌 CTL·TSB 감각(주 5~8 ramp, TSB −10~−30 훈련 구간)과 숫자가 맞지 않아 P3(Provider 투명성)가 성립하지 않는다. ACWR은 Williams(2017)의 EWMA-ACWR 관례대로 `2/(N+1)`를 쓰는 것이 맞지만, PMC까지 같은 계수를 공유한 것이 원인이다.
- 개선안: (1) PMC는 `α = 1 − exp(−1/τ)`(≈1/τ)로 바꾸고, ACWR만 별도 EWMA(2/(N+1))를 유지한다. (2) 워밍업은 CTL 계산에 최소 3τ(126일) 이상 쓰거나 전일 CTL을 이어받아 계산한다. (3) 레지스트리에 `time_constant_days`를 명시하고 상세 화면 정의 블록에 "CTL = TRIMP의 42일 지수가중평균(τ=42)"을 적는다. (4) Intervals CTL과의 비교를 Provider 매트릭스에 넣어(현재 SEMANTIC_GROUPS에 없음) 척도 차이를 드러낸다. (5) 재계산 후 TSB 등급 밴드(F-DATA-02)를 재보정한다.

### [치명] F-DATA-02 TSB·UTRS 등급 밴드가 러닝 관행·서버 레지스트리와 어긋남 — 정상 훈련 구간을 "피로 누적/과부하"로 표시
- 현상: 브라우저 핵심 지표 "폼 (TSB) −14.7 ● 피로 누적"(amber). 클라이언트 밴드는 −20 미만 "과부하(red)", −20~−10 "피로 누적", −10~5 "균형", 5~25 "레이스 최적"이다.
- 근거: `frontend/src/lib/metricMeaning.ts:26`(TSB 밴드), `:29`(UTRS/CRS 40/60/80). 서버 레지스트리 UTRS ranges는 `utrs.py:22` `poor 0-30 / low 30-50 / moderate 50-70 / good 70-85 / excellent 85-100`으로 경계가 다르다. Intervals.icu/Friel 관례는 −10~−30 "Optimal(훈련 적응 구간)", −30 미만 "High risk", +5~+25 "Fresh"이다.
- 왜 문제인가: 빌드업 중인 러너(마라톤 목표, 현재 주 43km)에게 TSB −15는 계획대로 훈련 자극이 쌓이고 있다는 신호인데, 화면은 경고색으로 휴식을 암시한다(P1 근거 없는 결론, 치명 기준 "잘못된 정보로 오판 유도"). 반대로 F-DATA-01 때문에 이틀만 쉬어도 +15 "레이스 최적"이 떠서 테이퍼 판단도 오도한다. UTRS 59는 클라이언트에서 "보통"이지만 서버 기준으로는 moderate의 상단이다. 같은 지표의 등급이 두 곳에 따로 정의되어 있다(CIRS 이원화는 ux.md F-UX-05 참조).
- 개선안: 등급 밴드의 단일 출처를 서버 레지스트리 `ranges`로 정하고, API가 `status`와 `band_label`을 내려주게 한다. 클라이언트 `meaningFor`는 제거한다. TSB 밴드는 τ 수정 후 관례값(< −30 위험 / −30~−10 훈련 / −10~+5 전환 / +5~+25 레이스 준비 / > +25 디트레이닝)으로 두고, 목표 레이스 D-day가 21일 이내일 때만 "레이스 최적" 문구를 쓴다.

### [치명] F-DATA-03 Provider 매트릭스: provider마다 다른 활동(수영 포함)의 값을 한 행에 비교, 기간 선택은 무의미
- 현상: 재조회 결과 "훈련 부하" 행은 Garmin 7.18 / RunPulse 55.7이고 "⚠ 675.89%", 대표값은 Garmin이다. 캡처 시점에는 Garmin 110이었다. `days=28`과 `days=84` 응답은 9개 행이 모두 **완전히 같다**.
- 근거: `src/services/provider_matrix_service.py:83-94`. canonical 활동을 최신순으로 돌며 provider마다 **처음 발견한 값**을 채우므로, 각 셀이 서로 다른 활동에서 올 수 있고 종목 필터도 없다. DB 확인: Garmin 7.18은 activity 17445(2026-09-27 14:09 **swimming** 525m), RunPulse 55.7은 17404(같은 날 07:00 러닝 9.3km)의 `hrss`다. 서비스 docstring(`:7-10`)이 "평균/합산 아님, 기간 내 가장 최근 활동 값"이라고 적고 있어, 4/8/12주 선택은 최근 활동이 없을 때만 결과에 영향을 준다.
- 왜 문제인가: 매트릭스의 목적(P3, 소스 간 차이 파악)과 반대로, ⚠ 경고가 **종목·활동 불일치에서 생긴 가짜 차이**를 알린다. 대표값 규칙이 이런 경우 Garmin을 고르므로 "훈련 부하 대표값 = 수영 7.2"가 된다. 러너는 이 표로 "Garmin 부하와 RunPulse 부하 중 무엇을 믿을까"를 판단할 수 없다.
- 개선안: 비교 단위를 **같은 활동 그룹(matched_group) 내부**로 고정한다. (a) 행 = 메트릭 그룹, 셀 = 기간 내 러닝 활동들에서 **동일 그룹에 대해 양쪽 값이 모두 있는 쌍**의 중앙값, 그리고 쌍별 차이의 중앙값·IQR·표본 수 n이다. (b) `activity_type IN ('running','trail_running','treadmill')` 필터를 둔다. (c) ⚠ 기준은 "쌍 차이 중앙값"으로 바꾸고 n<3이면 판정을 생략한다. (d) 기간 선택은 쌍의 표본 범위를 바꾸므로 의미를 갖게 된다. (e) 셀 탭 → 쌍 목록(날짜·활동·두 값)으로 드릴한다(ux.md F-UX-07의 행 클릭 요구와 결합).

### [치명] F-DATA-04 같은 활동에서 RunPulse 자체 계산값이 소스 사본마다 다름 — Relative Effort 302.3 대 27.7
- 현상: Provider 매트릭스 "상대적 노력도 ★27.7". 9.3km, 57분 러닝으로 보기에는 비현실적으로 낮다.
- 근거: DB `metric_store`(scope_type=activity, provider=runpulse:formula_v1)를 보면 같은 러닝의 두 사본에서 값이 다르다. Garmin 사본 17414는 relative_effort **302.3** / hrss 53.8 / wlei 99.73 / runpulse_vdot 32.7이고, Intervals 사본 17404는 **27.7** / 55.7 / 106.87 / 32.6이다. 9/26 러닝도 221.9 대 22.9로 같은 양상이다. 원인(코드 확인): `relative_effort.py`는 HR존 시간이 없으면 `avg_hr/max_hr` 비율로 전체 시간을 한 존에 몰아넣는 폴백을 쓴다(`:40-58`). Intervals 사본에는 존 데이터가 없어 Z1(계수 0.5)로 계산되었다(57.3분×0.5 ≈ 28, 추정). hrss·wlei 차이는 사본 간 duration(3318s 대 3436s, moving 대 elapsed) 차이로 보인다(추정).
- 왜 문제인가: "RunPulse — 자체 산출"이라고 한 값이 어느 사본을 입력으로 썼느냐에 따라 11배 달라진다. 이 값은 매트릭스에 그대로 나오고, 부하 계열 지표의 입력이 될 수 있다. 사용자는 이 차이를 알 수 없다(P3 위반, 틀린 수치).
- 개선안: RunPulse activity-scope 계산은 **그룹당 1회, 대표 사본(primary_source) 기준**으로 수행하고 결과를 group 단위로 저장한다(또는 대표 사본에만 저장). 존 시간은 스트림이 있는 사본에서 가져온다. 폴백 추정을 쓴 결과는 `confidence ≤0.6`과 `json_value.method='avg_hr_fallback'`으로 남기고, 화면에는 "추정" 배지를 단다. 데이터 정합성 검사(`/check-data-consistency`)에 "같은 그룹 사본 간 RunPulse 값 편차 >10%" 검사를 추가한다.

### [중요] F-DATA-05 매트릭스 그룹 정의 오류: 이름 불일치로 빈 셀, 이질 지표 혼합, 단위 없는 비교
- 현상: "러닝 효율성 ⚠ Intervals ★1.7 / RunPulse 20.4"(⚠ 1087%), "VO2Max ⚠ ★53 / 32.6"과 "VDOT ⚠ ★53 / 32.6"이 같은 숫자로 두 번 나온다. "환경별 성과 ★357"은 단위 없이 표시되고, "훈련 부하"에 Intervals 칸은 "—"이다.
- 근거: `src/utils/metric_groups.py`. DB에서 activity-scope 행 수를 세면 `training_load_score` 0건, `decoupling`(intervals) 0건, `trimp`(intervals) 0건, `suffer_score` 0건, `effective_vo2max` 0건, `vdot_adj` 0건이다. 반면 Intervals 부하는 `training_load`라는 이름으로 **612건** 있다(9/27 러닝 61). 설계상 4-provider 비교 행이 구조적으로 빈다. `running_efficiency`는 `rec`(0~100 백분위, daily), `efficiency_factor_rp`(m/s/bpm×1000 ≈ 20, `rec.py:9` 주석), Intervals EF(≈1.7)를 한 그룹에 넣었다. `vo2max`와 `vdot` 그룹의 멤버가 사실상 같다. `seasonal_performance`의 357은 `fearp` = 356.5 s/km, 즉 **5:57/km 페이스**다. 행마다 `"unit": null`이다(`provider_matrix_service.py:121`). 한 셀에 그룹 멤버 중 무엇이 들어갔는지(hrss/wlei/rtti) 표시하지 않는다.

## 최우선 개선 3개
1. **부하 엔진 정정과 등급 단일화**(F-DATA-01, 02, 08, 10): PMC를 α=1/τ(42/7)로 바꾸고 워밍업 126일 이상 + 전일 연속 계산을 적용한다. ramp를 주간으로 바꾼다. 등급 밴드는 서버 레지스트리 단일 출처로 하고 TSB는 관례 밴드를 쓴다. 부하 대표는 ACWR·TSB 두 개와 통합 판정 한 줄로 한다. 재계산 후 Intervals CTL과 병행 비교하고, 수집 복구(F-DATA-12)로 검증한다.
2. **Provider 비교를 "같은 활동 쌍" 기준으로 재구축**(F-DATA-03, 04, 05): 비교를 matched_group 쌍의 차이 중앙값·n으로 하고 러닝 종목만 대상으로 한다. 그룹 멤버를 DB 실재 이름과 동일 단위로 교정하고 LTHR·CTL·일 부하 행을 추가한다. RunPulse activity 계산을 그룹당 1회로 하고 폴백은 "추정"으로 표시한다. 정합성 검사 2종(그룹 멤버 존재, 사본 간 편차)을 추가한다.
3. **예측·준비도 분해를 저장된 근거로 채우기**(F-DATA-06, 07, 11): 분해 API가 `json_value`를 구조화해 반환하도록 한다. 예측은 범위·신뢰도·모델 혼합·신호 가중·원천 활동·개선 요인으로, UTRS는 원시 입력·기준선·가중 손실 점수로 보여 준다. UTRS 스냅샷은 기상 시점으로 고정하고 HRV는 개인 기준선 z-score로 정규화한다. 웰니스 카드에는 기준선 대비 편차와 누적값 기준 시각을 붙인다.
