# Library · 메트릭 브라우저·메트릭 상세·웰니스·Provider 비교 — UX(사용자 경험·흐름) 리뷰

요약:
1. "왜 이 숫자가 이런가"(Library의 의도, P4)를 풀 경로가 끊겨 있다. Today의 지표는 제자리 분해 시트로만 열리고 Library 메트릭 상세로 가는 링크가 없다. 메트릭 상세의 차트 포인트는 스크럽 판독만 되고, 분해는 항상 "최신일" 기준이라 과거 날짜의 원인을 볼 수 없다. D1→D3(값→분해→원천 날짜·활동)이 **어느 메트릭에서도 성립하지 않는다**.
2. 분해가 "라벨 + 정규화 값" 나열이다. UTRS 분해에 `(parent: utrs)` 내부 식별자가 그대로 보이고, 가중치·기여 점수·"무엇이 끌어내렸나"가 없다. 가중치는 코드에 있어(UTRS BB .30/TSB .25/수면 .20/HRV .15/스트레스 .10) 계산하면 **"TSB가 18.5점, 수면이 9.6점을 깎았다"**는 결론이 나오는데, 화면은 이 결론을 주지 않는다.
3. 지표 설명 경로가 없다. 52개 daily 메트릭 중 해석 문구가 붙은 것은 6개뿐이다(`metricMeaning.ts`). 백엔드 레지스트리에는 설명·방향(높을수록 좋음)·범위가 있지만 UI는 쓰지 않는다. RTTI 130%, SAPI 105, REC 78.4 같은 수치는 처음 보는 러너에게 뜻이 없다.
4. 메트릭 상세는 목록에서 본 포맷과 다른 결과를 보여 준다(이 탭의 치명 이슈). 목록에서 `3:40:23`이던 마라톤 예측이 상세에서는 `13223.0 sec`로 나오고, "피크"는 가장 느린 기록(13624 sec)을 가리킨다. 차트 방향도 향상이 아래로 향한다. 같은 CIRS 37을 Today는 "주의", 브라우저는 "보통"으로 표시한다.
5. 웰니스는 읽기 전용 대시보드에서 멈춘다. 수치 클릭이 무반응이고, 일자 상세가 없으며, 기준선 대비 해석이 없어 회복 판단 흐름이 없다. Provider 비교는 "왜 여는가"가 없고 행동으로 이어지지 않는다(단위 없음, 행 클릭 불가, 대표값 이유는 hover에만 있음).

## 발견

### [치명] F-UX-01 메트릭 상세가 목록과 다른 포맷·반대 의미로 표시됨 (예측 기록 원시 초, "피크"=최악, 방향 반전)
- 현상: 브라우저 카드 `마라톤 예측 기록 3:40:23`을 누르면 상세 헤더가 `마라톤 예측 기록 (sec)`, 현재 값이 `13223.0 sec`로 바뀐다. "피크" 카드는 `13624.0 sec (2026-08-25)`로, 1년 중 **가장 느린** 예측을 최고점처럼 보여 준다. 차트는 기록이 줄면(향상) 선이 내려간다. 분해 시트도 `13223 sec`다. 깊은 수면도 `3420.0 sec`, 피크 `8040.0 sec`로 나온다(분 단위 아님).
- 근거: `metric-race_pred_marathon-breakdown-desktop.png`, `metric-sleep_deep_sec-desktop.png`, `raw/library-metrics.txt`(3:40:23). 코드 `routes/library/metrics/[slug]/+page.svelte:72`(`current.toFixed(1)`), `:28-32`(`formatPeak` = 방향 무시 toFixed), `:92-95`(TrendChart에 `formatValue` 미전달. 컴포넌트는 prop을 지원함 `TrendChart.svelte:11`). `MetricBreakdown.svelte:74`(`data.value` 원값). API `/library/metrics/race_pred_marathon_sec` → `"unit":"sec","value":13223.0`(확인).
- 왜 문제인가: U2·U3 정면 위반이다. 목록→상세로 한 번 탭했을 뿐인데 같은 수치의 표기가 바뀌어 신뢰가 깨진다. "피크"를 최고 성과로 읽으면 8/25를 최고 컨디션으로 **오판**하게 된다.
- 개선안:
  - 목록·상세·분해·차트 판독에서 **하나의 포맷터**를 쓴다: `formatMetric(slug, value)`. 내부적으로 `formatUnitValue`와 메트릭별 방향 메타를 쓴다. 표기는 `3:40:23`, `57분`, `4:38/km`.
  - 방향 메타(`higher_is_better`, `metrics/base.py:55`에 존재)를 API로 내려 준다. 요약 카드의 "피크" 라벨을 방향에 따라 **"최고 기록 3:34:11 (2026-02-14)"** 또는 **"최고 60.2 (…)"**로 바꾼다.
  - 시간·페이스 계열 차트는 y축을 반전해 "위 = 더 빠름"으로 그린다. 축 상단에 작은 캡션 `↑ 빠름`을 둔다.
  - 30일 변화도 방향을 반영한다: `-2.7% (6분 빨라짐)`을 초록으로 표시.

### [치명] F-UX-02 "왜?" 경로 단절: Today→Library 컨텍스트 없음, 차트 포인트→분해·원천 불가 (P2 D1→D3 미성립)
- 현상:
  - Today의 UTRS/CIRS/TSB 칩은 제자리 분해 시트만 연다. 시트에는 "이 지표의 추세·과거 보기 →"가 없다. Today→Library 링크는 "Library에서 전체 탐색 →"(Library 홈) 하나뿐이다.
  - 메트릭 상세의 차트를 클릭하면 판독만 바뀐다(textDelta 0). 분해 시트는 **항상 최신일**만 연다. 8/08 피크(89.4)나 오늘 급락(-12%)의 원인을 날짜 단위로 볼 수 없다.
  - 분해의 "입력 메트릭"(TSB -14.4)은 상세 페이지에서 disabled다. 원천 활동(TSB를 만든 최근 부하 세션)으로 가는 링크는 어디에도 없다.
- 근거: `raw/interact-desktop.json` "Metric UTRS: 차트 클릭" → IN_PAGE_CHANGE, textDelta 0. `[slug]/+page.svelte:120-126`(`scopeId={latestDate}` 고정, `onDrillInput` 미전달). `MetricBreakdown.svelte:106-111`(onDrillInput 없으면 disabled). grep 결과 `routes/today`에 `library/metrics` 링크 0건(확인).
- 왜 문제인가: Library의 존재 이유(P4 "왜 이 숫자가 이런가")와 P2(3단 이내 원천)의 핵심 과업이 불가능하다. 지금은 값(D1)→구성 값 나열(D2)에서 막다른 길이다.
- 개선안(라우트·상태 설계):
  - 라우트 `/library/metrics/:slug?date=YYYY-MM-DD&period=3m&from=today`를 쓴다. `date`는 차트 선택점과 분해 기준일이다.
  - 차트: 탭(모바일)/클릭(데스크톱)하면 해당 날짜에 **고정 커서**를 두고, 차트 아래 인라인 "이 날의 분해" 패널을 즉시 그 날짜로 갱신한다. 바텀시트 대신 페이지 내 섹션을 쓰고, `replaceState`로 `?date=`를 반영한다.
  - 분해 패널 하단에 **"이 날의 원천"** 목록을 둔다. 예: `9/26 롱런 28.1km (TRIMP 212) — TSB를 -6 끌어내림 → 활동 상세`, `9/27 수면 4h14m → 웰니스 9/27`. 이렇게 D1(값)→D2(분해)→D3(활동/웰니스 일자)을 **2탭**으로 만든다.
  - 입력 메트릭 행은 `/library/metrics/tsb?date=같은날짜`로 이동한다(드릴 스택 유지).
  - Today의 분해 시트 헤더에 `추세·과거 보기 →` 링크(`/library/metrics/utrs?date=오늘&from=today`)를 추가한다. 상세의 ←는 `from`에 따라 "← Today"로 표시한다.

### [치명] F-UX-03 계산 분해가 단순 나열: 내부 ID 노출, 가중치·기여도·결론 부재 (U6)
- 현상: UTRS 분해 시트는 `UTRS 구성요소 - TSB 정규화값 (parent: utrs) 26`, `… Body Battery 정규화값 (parent: utrs) 76` 5행, 입력 `Training Stress Balance -14.4`(영문)로 끝난다. 합산 방식·가중치가 없어 59.4가 어떻게 나왔는지 재현할 수 없다. 마라톤 예측 분해는 값 한 줄뿐이다(children·inputs 빈 배열, confidence 0.36은 미표시).
- 근거: `metric-utrs-breakdown-desktop.png`, `metric-race_pred_marathon-breakdown-desktop.png`. `MetricBreakdown.svelte:90`(child.label 원문 출력. `displayLabel` 미사용 — `metricMeaning.ts:57`에 같은 목적의 함수가 있음). API `/library/metrics/utrs?scope_id=2026-09-27` 응답에 weight 필드 없음(확인). 가중치는 `src/metrics/utrs.py:32-38`, `cirs.py:34-39`(확인).
- 왜 문제인가: 사용자 지적 "분해가 단순 나열"이 그대로 재현된다. 러너가 얻어야 할 결론인 **"왜 59점인가, 무엇을 바꾸면 오르나"**가 없다. 투명성(비전 원칙 2)이 형식만 있다.
- 개선안(분해 패널 구조):
  1. **결론 한 줄(Level 0)**: `준비도 59 — 누적 피로(TSB)가 가장 크게 끌어내렸어요 (-18.5점). 다음은 짧은 수면 (-9.6점).`
  2. **기여 워터폴 바**: 100점 만점 기준 손실을 막대로 보여 준다. 실제 값 계산(확인):
     | 요소 | 내 점수 | 가중치 | 기여 | 만점 대비 손실 |
     |---|---|---|---|---|
     | Body Battery | 76 | 30% | 22.8 | -7.2 |
     | 폼(TSB) | 26 | 25% | 6.5 | **-18.5** |
     | 수면 점수 | 52 | 20% | 10.4 | -9.6 |
     | HRV | 75 | 15% | 11.3 | -3.8 |
     | 스트레스(역산) | 84 | 10% | 8.4 | -1.6 |
     | 합계 | | | **59.4** | |
     CIRS(36.6)도 같은 형식이다. 연속훈련일 57.1×20%=11.4, 피로 100×10%=10.0, LSI 24×30%=7.2, ACWR 20×40%=8.0. 결론: `위험도를 가장 올린 건 연속 훈련일(11.4)과 누적 피로(10.0)`.
  3. **무엇을 바꾸면(what-if)**: `오늘 쉬고 7시간 자면 → 내일 UTRS 약 68 예상 (TSB -8, 수면 75 가정)`. 가중치가 공개되어 있으므로 클라이언트 계산으로 추정만 표시하고 "추정"으로 표기한다.
  4. **원천**(F-UX-02)과 **공식 접기**: `UTRS = 0.30·BB + 0.25·TSB정규화 + … (formula_v1, 계산 2026-09-27 06:10)`. 정규화 규칙(TSB -30→0, +25→100 등)은 한 줄로 쓴다.
  5. 예측 기록처럼 children이 없는 메트릭은 빈 시트 대신 **입력 근거**를 보여 준다(사용한 VDOT·최근 기준 활동·신뢰도 36% "낮음 — 최근 레이스급 기록 부족").
  - 라벨은 `displayLabel`/한국어 레지스트리 라벨로 통일한다(`Training Stress Balance`→`폼(TSB)`).
  - 참고: WHOOP Recovery의 "기여 요인" 막대, Oura Readiness의 기여 요소 목록에 붙는 "Pay attention/Optimal" 라벨. RunPulse는 여기에 **가중치·손실 점수**를 공개해 두 앱보다 투명해질 수 있다(시그니처 모먼트 후보).

### [중요] F-UX-04 처음 보는 지표를 이해할 경로 없음: 설명·좋은 범위·해석 부재 (U5)
- 현상: 브라우저 카드 대부분은 이름·숫자·스파크라인뿐이다. `달리기 내성 지수 (RTTI) 130%`, `SAPI (계절 성과 비교) 105`, `RRI (레이스 준비도) 60.4`, `Load Spike Index 1.2`, `훈련 단조로움 1.1`에 해석이 없다. 상세 페이지에도 설명 문단·범위 밴드·"그래서 무엇을"이 없다. 해석 라벨이 붙는 것은 `meaningFor`의 tsb/utrs/crs/cirs/acwr 등 6종뿐이다.
- 근거: `library-metrics-desktop.png`. `metricMeaning.ts:22-43`(switch 6종). `[slug]/+page.svelte` 전체에 설명 요소 없음. 백엔드 `MetricDef.description`(`metric_registry.py:36`), `ranges`·`higher_is_better`(`metrics/base.py:52-55`), 사전 `metric_dictionary.md:303-313`("수면, HRV, 체력 상태, 스트레스를 종합한 훈련 준비도… 높을수록 좋음")은 존재하지만 UI에 노출되지 않음(확인).
- 왜 문제인가: 사용자 지적 "지표 설명·의미가 부족하다"와 U5 4요소(무엇/좋은 범위/내 값 해석/그래서 무엇을)가 모두 빠져 있다. 페르소나는 "데이터 과학자는 아님"이다. 약어가 과잉(UTRS·CIRS·CRS·RRI·RTTI·SAPI·REC·LSI·ACWR)이고, "레이스 준비도"가 카테고리명이자 RRI 이름으로 겹쳐 혼동을 준다.
- 개선안:
  - **상세 상단 "이 지표는" 블록(Level 0~1)**: ① 한 줄 정의(평이한 말) ② 좋은 범위 밴드(차트 배경에 초록/노랑/빨강 가로 띠, 현재 값 마커) ③ 내 값 해석 `지금 59 — 보통. 최근 90일 내 평균(71)보다 낮아요` ④ 행동 `강도 높은 세션은 TSB가 -10 위로 회복된 뒤로`. 개인 기준선(90일 p25~p75)을 기본 비교축으로 쓴다(WHOOP/Oura 방식).
  - **용어 칩**: 약어 옆 `ⓘ`를 누르면 팝오버로 풀네임·한 줄 정의·"자세히 →"(상세)를 보여 준다. 모든 화면(Today·활동 상세·Coach)에서 같은 컴포넌트 `MetricTerm`을 쓴다.
  - 브라우저 카드 2행에 `의미 한 줄`을 필수로 둔다(meaningFor가 없으면 레지스트리 description 축약). 예: `RTTI 130% · 평소 대비 달리기 부하를 30% 더 견디고 있음`.
  - 라벨 정책: 한국어 의미어를 먼저, 약어는 괄호로. 표시 이름은 레지스트리 한 곳에서 관리한다(현재 `LABELS` 8개 하드코딩 → API `display_name`).
  - 데이터 전달은 `/library/metrics`·`/:slug/trend` 응답에 `description`, `direction`, `bands`, `baseline`을 추가하는 방향을 제안한다(구조 결정은 system-architect 영역).

### [중요] F-UX-05 같은 수치, 다른 해석: CIRS 37이 Today "주의" / 브라우저 "보통"
- 현상: Today 요약 칩은 `37 CIRS 주의`, 메트릭 브라우저 카드는 `부상 위험도 (CIRS) 36.6 ● 보통`, 웰니스는 라벨 없이 `37`이다. TSB -15는 Today에서 "주의", 브라우저에서 "피로 누적"이다.
- 근거: `raw/today.txt`(CIRS 주의), `raw/library-metrics.txt`(● 보통). 브라우저는 클라이언트 `metricMeaning.ts:37`(30~50 neutral '보통')를 쓰고 Today는 서버 status를 쓴다(`MetricCell.svelte:36-38`) — 해석 소스가 이원화되어 있음(확인).
- 왜 문제인가: 탭 간 흐름(U8)에서 신뢰를 직접 깨뜨린다. "주의라더니 여기선 보통?"

- 핵심 지표 8개를 상단에 크게 두고, 나머지 보조 카테고리를 접은 1차 위계 설정.
- 브라우저 카드 전체가 링크(`<a>`)이고 상세 이동이 148~195ms로 빠름.
- 메트릭 상세의 기간이 URL(`?period=`)에 반영되어 공유·새로고침에 강함(replace로만 바꾸면 됨).
- `TrendChart`의 포인터 스크럽 판독(모바일 `touch-action: pan-y`)은 U1 해결의 좋은 기반이며, `formatValue` prop도 이미 존재.
- 구성요소 메트릭을 그리드에서 숨기고 상위 분해에서 보이게 한 방향성, Provider 매트릭스의 ★/⚠ 개념.
- 데이터 부족 시 "데이터 수집 중" 빈 상태 일관.

## 채점 (0~10, 한 줄 근거)
- 비전 부합: **4** — 투명성·소스 비교의 뼈대는 있으나 "왜"를 결론으로 번역하지 못함.
- 정보 정확성: **3** — 원시 초·방향 무시 "피크"·CIRS 등급 이원화로 오판 유도.
- 시각 품질: **5** — 절제된 카드 그리드. 상세·웰니스는 축 없는 스파크라인과 빈 여백.
- 상호작용 반응성: **5** — 이동 150ms로 빠르나, 브라우저 1.4s 무피드백·웰니스 무반응·분해 점프.
- 흐름: **2** — Today→Library 컨텍스트 없음, 차트→분해→원천 불가, 서브탭 소실, 필터 리셋.
- 혁신성: **3** — 가중치 공개 분해·소스 비교라는 시그니처 재료를 가졌지만 화면에서 드러나지 않음.

## 최우선 개선 3개
1. **분해를 "결론 + 기여 워터폴 + 무엇을 바꾸면 + 원천 날짜·활동"으로 재설계**(F-UX-03, F-UX-02). 차트 포인트 탭 → 그 날짜의 분해 → 원천 활동/웰니스 일자까지 2탭. `?date=` 라우트, Today 분해 시트에서 "추세·과거 보기 →" 연결.
2. **표시 일관성 단일화**(F-UX-01, F-UX-05, F-UX-12). 하나의 포맷터(h:mm:ss·분·페이스), 방향 메타 기반 "최고/최악"·축 반전, 서버 단일 등급 밴드, 한국어 표시명 통일.
3. **지표 이해 경로 + 탐색 구조**(F-UX-04, F-UX-08, F-UX-09, F-UX-06). 상세 상단 "이 지표는" 블록(정의·좋은 범위 띠·개인 기준선 대비 해석·행동), 약어 `ⓘ` 용어 칩, 검색·고정·URL 필터, Library 공통 서브탭 레이아웃, 웰니스 일자 라우트와 클릭 가능한 기준선 대비 카드.
