# Library 홈 · 활동 목록 · 활동 상세 — 러닝 데이터 전문가 리뷰

**리뷰일**: 2026-09-27 · **대상**: `/v2/library`(아카이브 홈), `/v2/library/activities`(목록), `/v2/library/:id` 요약·스트림·랩·메트릭·소스 비교
**검증 표본**: 17414(오늘 이지 9.3km, Garmin+Intervals 병합), 15302(롱런 24.2km), 910(경주 마라톤), 13647(트레일 12km, 누적 상승 665m)
**방법**: 화면(`screenshots/activity*`, `library*`, `raw/*.txt`)을 API(`/api/v1/library/archive`, `/activities/:id`, `/activities/:id/providers`, 읽기 전용 GET)와 대조하고, 다시 DB(`metric_store`, `activity_streams`, `race_results`, 읽기 전용 sqlite)와 계산 코드(`src/metrics/*`, `src/services/*`, `frontend/src/lib/*`)로 확인했다.
UI(차트 방향·스케일·포맷)와 UX(흐름·세션 유형별 해석)는 같은 폴더의 `ui.md`·`ux.md`에서 다룬다. 이 문서는 **수치가 맞는지, 러닝 관행에 맞는지**만 본다.

요약:
1. **Relative Effort가 대부분의 러닝에서 5~10배 부풀려져 있다.** 존 데이터가 없으면 "평균심박 ÷ **그 활동의** 최대심박"으로 존을 정한다. 그래서 이지런(137/147=0.93)이 전부 Z5로 잡혀 302 AU가 되고, 마라톤은 1,221 AU가 된다. 캐노니컬 러닝 347건 중 341건이 이 대체 경로를 탄다(평균 203, 존 기반 평균 55). 같은 러닝이 소스 비교 탭에서는 27.7이다(확인).
2. **KM 스플릿·"이 러닝의 이야기"가 정지 시간을 페이스에 넣는다.** 구간 시간을 경과시간(elapsed)으로 재기 때문이다. 17414의 마지막 0.3km는 12:12/km로 나오지만 같은 구간의 랩은 5:35/km다. 롱런 15302에서는 신호 대기·급수 5회(430초)가 5개 km를 6:21~7:21로 만들었고, 이 값이 전후반 판정과 디커플링 11.2%에 그대로 들어갔다(백엔드 디커플링은 6.07%).
3. **CTL/ATL이 표준보다 약 2배 빠르게 반응한다.** 감쇠 계수로 `2/(N+1)`를 쓰기 때문이다. 그래서 "이 날 체력(CTL)"이 롱런 한 번에 +9.3, 마라톤 하루에 +18.7로 나온다. 오늘 값은 하루 중 계산 시각에 따라 바뀐다(캡처 당시 +2.8/−15, 지금 +1.6/−9.0).
4. **소스 비교는 서로 다른 양을 한 행에 놓고 "소스 간 차이"로 경고한다.** VO2max와 이지런 VDOT, Garmin 부하와 HRSS, 파워 기반 EF와 속도 기반 EF, 한 발 기준 케이던스가 그렇다. 게다가 RunPulse 열은 다른 형제 행(Intervals 행)에서 계산된 값이라 메트릭 탭과 숫자가 다르다(TRIMP 97.3/101, RE 302/27.7).
5. **"RunPulse GAP"에는 경사 보정이 없다.** Garmin 스트림은 `grade_pct`가 0/1,675로 비어 있고, 공식은 보정 방향이 반대다. 평지에서는 실제보다 느리게(6:02 vs 5:57) 나오고, 누적 상승 665m 트레일에서는 거의 보정되지 않는다(9:55, Garmin GAP 9:04).

## 발견

### [치명] F-DATA-01 Relative Effort가 활동 자신의 최대심박으로 존을 정해 5~10배 부풀려진다 — 요약 "핵심 메트릭" 카드에 노출
- 현상: 17414(이지, 평균 137bpm)의 요약 카드와 메트릭 탭은 `Relative Effort 302 AU`, 소스 비교 탭은 `상대적 노력도 27.7`이다. 롱런 15302는 278, 경주 마라톤 910은 **1,221 AU**다. 계산기 자체의 `ranges`로 보면 302는 `very_high`(200+)이고, 이지런이 최고 등급에 들어간다.
- 근거:
  - `src/metrics/relative_effort.py:47-66`: `metric_store`에 `hr_zone_N_sec`가 없으면 `ratio = avg_hr / act.max_hr`(**그 활동의 최대심박**)로 활동 전체를 한 존에 넣는다. 17414는 137/147=0.932 → Z5 → 54.97분×5.5=302.3(확인). 910은 147/158=0.93 → Z5 → 1,221.4.
  - 존 데이터는 Intervals 형제 행(17404)에만 있다(Z1 3,282s, Z2 20s). 그 행의 RE는 27.7이다(DB 확인).
  - 캐노니컬 러닝 중 RE 347건에서 341건이 대체 경로(confidence 0.6)다. 평균은 203이고, 존 기반(0.9) 6건 평균은 55다(DB 확인).
- 왜 문제인가: 틀린 수치로 부하를 판단하게 만든다(치명 정의). "이지런이 매우 높은 노력"이라는 신호는 회복 판단을 뒤집는다. 추세 차트나 코칭 근거로 쓰이면 오류가 누적된다. P3(출처 투명성)도 어긋난다. 같은 이름에 두 값이 있고 설명이 없다.
- 개선안:
  1. 대체 경로의 분모를 **선수 최대심박**으로 바꾼다(`max_hr_measured` → 최근 180일 최대. TRIMP의 `_get_max_hr`와 같은 규칙). 한 존에 몰아넣지 말고 스트림 심박으로 존 체류 시간을 직접 적분한다(스트림은 687건 보유).
  2. 존 경계는 선수 프로필(LTHR 또는 HRmax %) 하나로 통일하고, Intervals 존과 RunPulse 존이 다르면 소스 비교에서 보이게 한다.
  3. 재계산 전까지 confidence 0.6인 값은 카드에서 숨기고, 메트릭 탭에 `추정(존 데이터 없음)` 표시를 단다.
  4. 회귀 테스트: 평균/활동최대 ≥ 0.9인 이지런 픽스처에서 RE < 100.

### [치명] F-DATA-02 KM 스플릿·이야기 카드가 정지 시간을 페이스에 넣는다 — 전후반 판정·최고 구간·디커플링이 모두 오염
- 현상:
  - 17414의 마지막 부분 구간이 `0.3 12:12/km`로 나온다. 랩 탭의 같은 구간은 `0.3km 1:39 5:35/km`다.
  - 15302 스플릿 6·13·15·19·22km가 6:47·7:12·6:21·6:39·7:21/km로 튀는데, 모두 멈춘 구간이다. 이 값으로 "후반이 0:09/km 빨랐어요 — 네거티브 스플릿"과 "유산소 디커플링 11.2%(주황)"를 계산했다. 같은 활동의 메트릭 탭 디커플링은 6.07%다.
- 근거:
  - `frontend/src/lib/splits.ts:84-104`: 구간 시간 = 경계 통과 시각 차(`sampleTimes` = 스트림 `elapsed_sec`)라서 정지가 빠지지 않는다.
  - 17414 스트림: 3,218s(9,000m) → 3,347s(9,029m), 129초 동안 29m 이동(API 확인). elapsed 3,436 − timer 3,318 = 118s.
  - 15302 스트림 공백: 2,000→2,050s(5.4km), 4,618→4,714s(12.7km), 7,780→7,909s(21.6km) 등 6곳, 합계 430s. elapsed 8,767 − timer 8,357 = 410s(DB 확인).
  - 디커플링은 두 가지로 구현돼 있다. `runStory.ts:66-72`(km 스플릿 전·후반, 정지·워밍업 포함)와 `src/metrics/decoupling.py:45-64`(샘플 개수 절반 분할이라 Garmin smart recording에서는 시간 절반이 아님)이다. 결과는 17414 4.5 vs 4.4, 15302 11.2 vs 6.07, 910 −1.8 vs −1.64다.
- 왜 문제인가: 스플릿은 러너가 가장 먼저 읽는 표다. 도심 롱런은 신호 대기가 흔하므로 이 오류는 예외가 아니라 기본값이다. 5% 기준선을 두고 "주의(11.2)"와 "양호(6.07)"를 오가는 디커플링은 유산소 기반 판단(롱런 페이스 조정)을 뒤집는다. 스케일 문제는 `ui.md` F-UI-04, 세션 유형별 서사는 `ux.md` F-UX-08 참조.
- 개선안:
  1. 스플릿 시간은 **이동 시간**으로 잰다. 연속 샘플의 속도 < 0.5m/s이거나 Δt > 10s이면서 Δd < 5m인 구간을 정지로 보고 제외한다. Garmin timer와 ±2% 이내인지 테스트로 고정한다. 정지가 있었던 구간에는 `⏸ 1:36` 주석을 붙인다.
  2. 디커플링은 **백엔드 한 곳**(`aerobic_decoupling_rp`)만 쓴다. 식은 Friel 관행을 따른다. 첫 10분(워밍업)을 제외하고, 이동 시간 기준으로 절반씩 나누며, 정지 구간을 제외한다. 이야기 카드는 이 값을 읽기만 한다.
  3. 디커플링은 **정속 유산소 세션**(이지·롱런, 페이스 CV < 5%)에서만 판정 색을 붙인다. 네거티브/프로그레션 런은 페이스가 오르면서 심박도 오르는 게 정상이므로 `참고(속도 변화 큼)`로 표시한다.
  4. 부분 구간 판정 제외는 `ui.md` F-UI-04를 따른다.

### [치명] F-DATA-03 소스 비교가 서로 다른 양을 비교해 거짓 "⚠ 차이"를 내고, RunPulse 열은 다른 형제 행의 값이다
- 현상(17414, `raw/activity-providers.txt`): ⚠ 8개 중 실제 측정 차이는 상승·하강 고도와 기온 3개뿐이다. 나머지는 정의가 달라서 생긴 차이다.

  | 행 | 값 | 실제 |
  |---|---|---|
  | VO2Max / VDOT(행 2개가 같은 값으로 중복) | Garmin 53 vs RunPulse 32.6 | 기기 VO2max 추정 vs **이지런을 레이스로 가정한 VDOT**(F-DATA-07) |
  | 훈련 부하 | Garmin 110 vs RunPulse 55.7 | Garmin EPOC 부하 vs HRSS(Intervals 행 값). Intervals 자체 부하 61은 **빠짐** |
  | 러닝 효율성 | Intervals 1.72 vs RunPulse 20.45 (차이 1,087%) | 파워/심박 EF vs 속도(m/s)/심박×1000 |
  | 평균 케이던스 | 173 vs 87 | Intervals는 한 발 기준(spm/2) |
  | 환경별 성과 | `★357` 단위 없음 | FEARP 356.5**초/km**(=5:57/km)를 숫자로 표시 |
  | 임계 파워/페이스 | Intervals 289 | icu_ftp(W). 단위 없음, 이 활동의 값이 아닌 선수 설정값 |
  | TRIMP / 상대적 노력도 | 101 / 27.7 | 메트릭 탭은 97.3 / 302. 17404(Intervals 행)에서 계산된 값 |
- 근거:
  - `src/utils/metric_groups.py:24-128`: `training_load` 그룹에 Garmin 부하·HRSS·WLEI·RTTI를 섞었다. `vo2max`와 `vdot` 그룹은 둘 다 `runpulse_vdot`+`vo2max_activity`다. `seasonal_performance`에는 SAPI(지수)와 FEARP(페이스)가 섞였다. Intervals 부하는 `training_load_score`로 찾지만 DB 이름은 `training_load`다(17404 행 `training_load|intervals|61.0` 확인).
  - `provider_comparison_service.py:130-145`: 형제 id를 순회하며 먼저 발견한 값을 쓴다. 같은 RunPulse 계산이 형제 행마다 따로 저장되어 있다(17404: TRIMP 100.8, RE 27.7, HRSS 55.7, VDOT 32.6 / 17414: 97.3, 302.3, 53.8, 32.7). 원인은 duration 정의 차이다(Garmin timer 3,318s, Intervals `duration_sec`=elapsed 3,436s).
- 왜 문제인가: 소스 비교는 RunPulse의 signature(P3, U7)다. 그런데 러너가 "Garmin과 RunPulse가 62% 다르다 → 어느 VO2max를 믿어야 하나"로 오판하게 만든다. 진짜 차이(마라톤 910 상승고도 Garmin 135m vs Intervals 496m — 코스 난이도 해석이 달라짐)는 가짜 경고 사이에 묻힌다.
- 개선안:
  1. **비교 행은 같은 정의끼리만** 묶는다. 그룹 스키마에 `quantity`(예: `vo2max_ml_kg_min`, `load_epoc`, `load_trimp`, `ef_speed_hr`, `ef_power_hr`)와 `unit`을 필수로 둔다. quantity가 다르면 같은 행에 넣지 않고 "관련 지표"로 따로 보인다.
  2. 단위 정규화 계층: Intervals 케이던스 ×2, 페이스류는 `m:ss/km`로 포맷, 선수 설정값(FTP)은 활동 비교에서 뺀다.
  3. RunPulse 계산은 **캐노니컬 행 하나에만** 저장하거나, 비교 시 캐노니컬 행 값을 우선한다. 형제별 계산 차이는 입력 차이(timer vs elapsed)라는 설명과 함께 개발자 모드에서만 보인다.
  4. 차이 판정 임계값은 항목별로 둔다. 고도는 절대 10m 미만 차이를 무시하고(17414의 5.3 vs 5.0 = 7.6%는 노이즈), 기온은 ±2°C, 시간은 정의가 같을 때만 비교한다.
  5. 표 위 요약은 진짜 차이만 센다: `측정 차이 1건: 누적 상승 Garmin 135m vs Intervals 496m — 기압계 vs DEM 보정`.

### [치명] F-DATA-04 CTL/ATL 감쇠가 표준의 약 2배 — "이 날 체력 +18.7", 오늘 값은 계산 시각마다 바뀐다
- 현상: "이 러닝의 의미"가 롱런 15302에 `체력(CTL) +9.3 · 폼(TSB) −44`, 마라톤 910에 `+18.7 · −77`을 보여준다. 캐노니컬 일별 CTL이 71.1(9/17) → 67.4(9/18, 휴식) → 69.9 → 79.2(9/20) → 75.0 → 71.5로 하루에 3~9씩 출렁인다. 17414는 캡처 시 `+2.8 / −15`였고 지금 API는 `ctl_delta 1.6, tsb −9.0`이다.
- 근거:
  - `src/metrics/pmc.py:51-52`: `atl_decay = 2/(7+1)=0.25`, `ctl_decay = 2/(42+1)=0.0465`. Banister/TrainingPeaks/Intervals 관행은 1/42(0.0238), 1/7(0.143)이다(또는 1−e^(−1/τ)). 지금 식의 CTL 실효 시정수는 약 21일, ATL은 약 3.5일이다.

- 개선안:
  1. `α = 1 − exp(−1/τ)`(τ=42/7)로 바꾸고, 워밍업은 전체 이력(최소 180일)으로 늘린다. 변경 전후 CTL을 Intervals `ctl`(보유 시)과 비교하는 회귀 테스트를 추가한다.

  4. 정의 변경은 `decisions.md`에 ADR로 남기고 `21-library-metrics`의 CTL 상세 설명과 맞춘다.

- 비전 부합 **5** — 4소스 병합·출처 표기·계산 방법 노출의 뼈대는 있다. 형제 소스 데이터(존·날씨·Intervals 부하)가 버려지고 비교가 거짓 경고를 낸다.
- 정보 정확성 **3** — 합계·기본 수치는 정확하다. 그러나 RE 5~10배, 정지 포함 스플릿, 2배 빠른 CTL, 보정 없는 GAP, 환산 PB 등 러너가 판단에 쓰는 파생 수치가 틀렸다.
- 시각 품질 **5** — 데이터 관점에서 단위 누락(357, 289), 소수점 심박, 원시 부동소수가 있다(시각 전반은 `ui.md`).
- 상호작용 반응성 **5** — 데이터 측면 해당 적음. 서브탭마다 650KB 재요청(`ux.md` F-UX-10).
- 흐름 **4** — 요약 → 메트릭 → 소스 비교 사이에서 같은 이름의 값이 바뀐다(TRIMP 97.3/101, RE 302/27.7, 디커플링 11.2/6.07).
- 혁신성 **5** — 세션 서사·소스 비교·환경 보정(FEARP)은 경쟁 앱에 없는 재료다. 수치 신뢰가 받쳐주지 않아 signature가 되지 못한다.

## 최우선 개선 3개
1. **파생 부하·체력 계산 교정**(F-DATA-01·04·09): RE 대체 경로를 선수 HRmax + 스트림 존 적분으로 바꾼다. PMC를 `1−e^(−1/τ)`와 전체 이력 워밍업으로 바꾸고 "이 러닝의 의미"를 활동 기여분으로 표시한다. 요약 부하는 TRIMP 1개와 개인 기준 비교로 정리한다. 재계산 후 Intervals CTL과 대조하는 회귀 테스트를 추가한다.
2. **구간·효율 지표를 이동 시간 기준으로 통일**(F-DATA-02·05): 스플릿·이야기·디커플링은 정지를 제외하고, 디커플링은 백엔드 단일 구현(Friel 방식)을 쓴다. GAP는 경사 스트림을 채우고 공식 방향을 고친다. 정속 세션에서만 판정 색을 붙인다.
3. **소스 비교·상세의 정의 정합성**(F-DATA-03·07·08): 그룹을 quantity·unit 기준으로 다시 짠다. RunPulse 계산은 캐노니컬 행 하나로 하고, 형제 소스 고유 데이터(존·날씨·Intervals 부하)는 상세에 병합한다. 날씨 category를 백필하고 활동 VDOT에 노력도 조건을 건다. 가짜 ⚠가 사라지면 "측정 차이 1건" 요약이 RunPulse의 signature가 된다.
