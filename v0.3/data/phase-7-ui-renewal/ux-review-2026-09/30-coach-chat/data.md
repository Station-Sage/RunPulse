# Coach 홈·대화 — 러닝 데이터 전문가 리뷰

**리뷰일**: 2026-09-27 · **대상**: `/v2/coach`(홈: 최근 대화·자주 묻는 주제·플랜 카드·컨디션 입력), `/v2/coach/:threadId`(대화·근거 칩·후속 질문)
**검증 방법**: 스레드 4개 전체를 `GET /api/v1/coach/threads/{1..4}`로 받아 답변 속 수치를 컨테이너 DB(`/app/data/users/pansongit@gmail.com/running.db`, `mode=ro`)의 `metric_store`·`daily_wellness`·`activity_summaries`·`user_inputs`와 대조했다. 답변 생성 경로는 `src/services/coach_service.py` → `src/ai/chat_engine.py` → `src/ai/chat_engine_rules.py` 순서로 따라가며 코드로 확인했다. 대화 전송(POST)은 하지 않았다.
**증거**: `coach-desktop.png`, `coach-mobile.png`, `coach-thread-desktop.png`, `coach-thread-mobile.png`, `coach-thread-evidence-desktop.png`, `coach-thread-evidence-mobile.png`, `coach-checkin-open-desktop.png`, `coach-checkin-open-mobile.png`, `raw/coach.txt`, `raw/coach-thread.txt`, 컨테이너 로그(`docker logs`, 읽기)

요약:
- **"오늘 훈련 조언"에 대한 답이 컨디션과 상관없이 항상 "피로 회복이 필요합니다"로 나온다.** 규칙 엔진은 회복 등급을 `A/B/C`로 비교하는데, 실제 등급 값은 `excellent/good/moderate/poor`이다. 그래서 첫 두 분기는 절대 실행되지 않는다. 바디배터리 100·수면 91·HRV 97이던 9/24에도 "휴식 권장"이라고 답했다. 지금 저장된 코치 답변 4개 중 3개가 이 버그의 산물이다.
- **근거 칩이 답변 결론을 뒷받침하지 않고 오히려 반박한다.** 칩은 답변을 만든 입력이 아니라 Today 브리핑의 근거를 그대로 복사해 붙인 것이다(`coach_service.py:27-33`). "피로 회복 필요" 답변 옆에 `TSB +3 (균형)`·`UTRS 81 (매우 좋음)` 칩이 붙어 있다(스레드 2).
- **답변 속 수치, 칩 라벨, 드릴 시트 값이 서로 다르다.** 칩에는 `TSB -11`이라고 적혀 있는데 누르면 `-3.3`이 뜬다. 9/23 답변의 TSB -16.5는 현재 DB에서 **+15.8로 부호가 반대**다. 답변이 "당시 값"이라는 표시도, 알고리즘 버전도 없다.
- **외부 LLM(Gemini→Groq)이 설정돼 있지만 모든 호출이 404로 실패하고, 조용히 규칙 답변으로 바뀐다.** 러너에게는 "규칙 기반 답변" 라벨만 보이고 실패 원인은 보이지 않는다. 외부로 보내는 데이터의 범위(30일 활동·웰니스·체크인 메모·DB 조회 도구 15종)도 어디에도 고지되지 않는다(P8).
- **"입력한 컨디션은 Coach 답변에 자동으로 반영됩니다"는 지금 경로에서는 사실이 아니다.** 규칙 답변과 Today 브리핑 모두 체크인을 읽지 않는다. 1~10 척도는 방향 라벨 없이 "어떻게 느껴지나요?"라고만 묻는데, 저장은 "피로도"로 해석된다. 좋은 날에 10을 누르면 "극도의 피로"로 전달된다.

## 발견

### [치명] F-DATA-01 회복 등급 비교 버그 — "오늘 훈련 추천"이 항상 "피로 회복 필요"로 고정된다
- 현상: "오늘 훈련 조언", "오늘 훈련 강도는?"에 대한 규칙 답변 3개(msg 8·12·14)가 모두 "피로 회복이 필요합니다. 가벼운 조깅이나 휴식을 권장합니다."로 시작한다. 그날 컨디션이나 TSB 값과 관계없이 똑같다. Coach 홈의 스레드 미리보기 3줄도 모두 같은 문장이다(`coach-desktop.png`).
- 근거:
  - `src/ai/chat_engine_rules.py:78-83` — `if grade in ("A", "B")` / `elif grade == "C"` / `else: "피로 회복이 필요합니다…"`.
  - `src/analysis/recovery.py:70-79` — `_recovery_grade()`가 돌려주는 값은 `"excellent"|"good"|"moderate"|"poor"`뿐이다. `A/B/C` 분기는 도달할 수 없는 코드다.
  - 실데이터: 9/24 `daily_wellness` BB 100·수면 91·HRV 97·스트레스 21, 9/25 BB 99·수면 87·HRV 107. 러너 입장에서 시즌 최고 수준의 회복 신호인데 두 날 모두 "휴식 권장"이 나갔다. 같은 경로의 msg10은 `회복 등급: excellent`를 스스로 출력하고 있다.
  - 오늘(9/27) 같은 질문을 보내도 결과는 코드상 같다(등급이 None이 아니든 None이든 else로 떨어진다). 같은 날 Today 헤드라인은 "컨디션 여유가 있어 핵심 세션을 소화하기 좋습니다"(`GET /api/v1/today` 확인)이므로, **Today와 Coach가 정반대 처방을 낸다.**
- 왜 문제인가: 틀린 결론으로 오판을 유도한다(심각도 정의 "치명"). 레이스 D-56 빌드 국면에서 "항상 쉬어라"를 따르면 훈련이 모자라게 되고, 무시하면 코치를 신뢰하지 않게 된다. 둘 중 어느 쪽이어도 Coach의 존재 이유가 무너진다. P1, P7, U10.
- 개선안:
  - 등급 키를 한 곳(`recovery.py`의 enum/상수)에서 정의하고 규칙 엔진은 그 상수를 import한다. `excellent/good → 고강도 가능`, `moderate → 중강도`, `poor → 회복`으로 매핑한다. `grade=None`(웰니스 없음)은 "회복 데이터 없음 — 부하 지표만으로 판단"이라고 명시한다.
  - 회귀 테스트: 등급 4종과 None 각각에 대해 `_respond_training_recommendation` 첫 문장을 단정하는 파라미터 테스트를 추가한다. 이 버그는 문자열 상수 불일치라 테스트 한 줄로 막을 수 있다.
  - Today 브리핑과 Coach 규칙 답변이 **같은 판정 함수**를 쓰게 한다(F-DATA-07). 두 화면이 다른 임계값 표를 따로 가지고 있는 한 모순은 다시 생긴다.

### [치명] F-DATA-02 근거 칩이 답변의 입력이 아니라 Today 브리핑의 근거다 — 결론을 반박하는 칩이 붙는다
- 현상:
  - 스레드 2 msg12: 결론은 "피로 회복이 필요합니다"인데 칩은 `TSB +3 (균형)`, `UTRS 81 (매우 좋음)`이다. 칩이 결론이 틀렸다고 말하고 있다.
  - 스레드 4 msg14: 결론은 "휴식 권장, 볼륨 줄이세요"인데 칩 4개 중 2개는 `42km 목표 D-58`, `레이스 아침 TSB +25 (테이퍼 시)`로 결론과 무관하다. 답변이 실제로 근거로 삼은 회복 등급(웰니스)은 칩에 없다(`coach-thread-desktop.png`).
- 근거: `coach_service.py:27-33` `build_evidence()`는 질문·답변과 관계없이 `get_today_briefing(conn)["evidence"][:5]`를 반환하고, `create_thread`/`add_message`가 이 값을 모든 어시스턴트 메시지에 붙인다(`:105`, `:141`). 그래서 "부상 위험 확인"이든 "목표 기록 가능할까?"든 칩은 늘 TSB/UTRS/D-day 조합이다. 후속 질문(`coachSuggestions.ts:21-30`)도 이 칩 메트릭 이름으로 만들어지므로, 질문과 무관한 칩이 무관한 후속 질문까지 만든다.
- 왜 문제인가: P1의 핵심은 "결론 옆의 근거가 그 결론을 만든 수치일 것"이다. 지금 칩은 "근거처럼 생긴 장식"이다. 러너가 칩을 읽고 답변과 모순을 발견하면 코치 전체의 신뢰가 무너진다. 칩을 읽지 않으면 P1 자체가 의미 없다. U6.
- 개선안:
  - 규칙 엔진과 LLM 경로가 모두 **답변과 함께 사용한 입력 목록**을 반환하게 한다. 예: `rule_based_response() -> (text, evidence)`에서 training 분기가 `recovery_score`(+등급·구성요소), `tsb`, `plan_today`를 evidence로 낸다. LLM 경로는 호출한 도구와 인용 수치를 evidence로 낸다.
  - evidence 항목에 `role: supports | caveat`를 둔다. 결론과 방향이 반대인 신호(예: "TSB는 균형이지만 수면 51")는 `caveat` 칩으로 따로 보여준다. 모순을 숨기지 않고 "이 신호는 반대 방향"이라고 설명하는 것이 코칭이다.
  - Today 브리핑 근거는 "Today 요약" 스레드처럼 브리핑을 설명하는 답변에만 쓴다.

### [치명] F-DATA-03 답변 속 수치, 칩 라벨, 드릴 값이 서로 다르다 — as-of 표시가 없다
- 현상: 스레드 4 칩 `TSB -11 (피로 누적)`을 누르면 시트에 `-3.3 RunPulse · formula_v1`이 뜬다(`coach-thread-evidence-desktop.png`). 한 화면에 같은 날짜(9/25)의 TSB가 -10.7(본문), -11(칩), -3.3(시트) 세 가지로 보인다. 스레드 1·2의 "TSB -16.5"(9/23)는 현재 DB 값 +15.8과 부호가 반대다.
- 근거: `GET /api/v1/library/metrics/tsb?scope_type=daily&scope_id=2026-09-25` → `value: -3.3`. DB의 9/21~9/27 TSB는 `-17.4, 2.2, 15.8, 2.6, -3.3, -2.9, -9.0`(`updated_at 2026-09-27 11:57` 일괄 재계산). evidence는 `value`와 `drill.scope_id`만 저장하고, 계산 버전이나 계산 시각은 저장하지 않는다(`coach_service.py:106`). 드릴 시트는 현재 값을 조회한다.
- 왜 문제인가: 틀린 수치를 보여주는 것은 치명 등급이다. 저장된 답변은 과거 계산의 스냅샷인데, 사용자는 그 사실을 알 수 없다. 칩과 시트가 다르면 "어느 쪽이 맞나"를 판단할 근거도 없다. 특히 TSB 부호가 바뀌면 "피로"와 "신선"이 뒤집힌다. 재계산 자체는 정당하다(중복 부하 정정으로 추정). 그러나 과거 답변이 그 사실을 드러내지 않는다. P3(계산 시각·버전), U8.
- 개선안:
  - evidence 스키마를 `{metric, value, scope, algorithm_version, computed_at}`로 확장한다. 드릴 시트는 "답변 당시 -10.7 (09-25 10:51 계산) → 현재 -3.3 (재계산 09-27)"을 두 줄로 보여준다.
  - 메시지 버블 하단에 "09-25 기준 데이터"를 항상 표시한다. 지금은 `staleLabel`이 7일이 지나야 뜨는데(`frontend/src/lib/threadAge.ts:7`), "오늘"로 시작하는 답변은 **다음 날부터** 이미 과거 이야기다. 임계값을 1일로 낮춘다.
  - 재계산으로 근거 수치가 ±5 이상 바뀌었거나 부호가 바뀐 답변에는 "근거 수치가 재계산으로 바뀌었습니다 — 다시 물어보기" 배너를 단다.

### [중요] F-DATA-04 외부 LLM이 전부 404로 실패하는데 조용히 규칙 답변으로 바뀐다 — 전송 범위 고지도 없다(P8)
- 현상: 사용자 설정은 `ai.provider = gemini`이고 gemini·groq 키가 모두 있다(컨테이너에서 `load_config` 결과는 키 존재 여부만 확인). 그런데 저장된 답변은 모두 `rule`이다. 컨테이너 로그에는 `Gemini API 오류: 404 Not Found …/v1beta/openai/chat/completions`, `Groq API 오류: 404 Not Found`가 오늘(09-27)만 8회 이상 찍혀 있다. 화면에는 버블 안에 회색 "규칙 기반 답변"(`localizeSource`, `frontend/src/lib/markdownLite.ts:73-77`)만 보이고, 실패 원인·설정 위치·재시도 방법은 보이지 않는다. 규칙 답변의 일반 분기는 아직도 "설정 > AI에서 Claude 또는 ChatGPT API 키를 입력하세요"라고 안내한다(`chat_engine_rules.py:262-263`). 키는 이미 입력돼 있다.
- 전송 범위: LLM 경로는 의도별 컨텍스트, Gemini용 30일 rich 컨텍스트(`chat_context_rich.py`), 체크인 피로·통증·**자유 메모**(`chat_context_checkin.py`)를 프롬프트에 넣는다. 여기에 더해 `tool_declarations.py`의 도구 15종(활동·랩·웰니스·날씨·러너 프로필 등)으로 DB를 임의 조회할 수 있다. v2 화면 어디에도 이 범위가 고지되어 있지 않다(`frontend/src`에서 외부/LLM/Gemini 문구 0건).
- 왜 문제인가: P8(3)을 정면으로 어긴다. 호출은 실패하지만 **요청 자체는 매번 외부로 나간다.** 러너는 데이터가 Google/Groq로 전송되는지도, 코치가 LLM이 아니라 키워드 규칙이라는 사실도 알지 못한다. 규칙 답변 품질(F-DATA-01·05)을 "AI 코치의 수준"으로 오인하게 된다.
- 개선안:
  - 답변 출처 라벨을 3상태로 나눈다. `Gemini 2.x · 도구 3회 사용` / `규칙 답변 (Gemini 오류 404 — 모델 설정 확인 →)` / `규칙 답변 (LLM 미설정)`. `chat()`이 `(text, provider, fallback_reason)`을 반환하게 해서 메시지에 저장한다.
  - 같은 provider가 연속으로 실패하면 Coach 홈 상단에 "AI 연결 오류 — 최근 N회 실패, 설정 확인" 배너를 띄운다(404는 모델 ID 폐기 가능성이 높음 — 추정).
  - 입력 바 위에 한 줄로 고지한다. "이 대화는 Gemini로 전송됩니다: 최근 30일 활동·웰니스·체크인 메모 + 필요 시 추가 조회 [범위 보기]". 범위 시트에는 도구 목록과 기간을 보여주고, 메모 제외 토글을 둔다.

### [중요] F-DATA-05 추천 질문과 후속 질문이 규칙 엔진에서 엉뚱한 답으로 라우팅된다
- 현상: LLM이 실패하는 지금, 모든 질문은 `chat_engine_rules.py:50-65`의 키워드 순서표로 분기된다. 화면에 제시되는 질문을 같은 규칙으로 돌려 보면 다음과 같다(분기 로직을 그대로 재현해 확인).

  | 화면의 질문 | 분기 | 실제 답 |
  |---|---|---|
  | 오늘 훈련 조언 | training | "피로 회복 필요"(F-DATA-01) |
  | 레이스까지 어떻게 훈련을 쌓을까? | race | 목표 이름·D-day·RRI 한 줄 — "어떻게 쌓을까"에 대한 답 없음 |
  | **목표 기록 가능할까?** | **training** ("가능할까"에 "할까"가 포함됨) | 오늘 훈련 추천 — 질문과 무관 |
  | 부상 위험 확인 | injury | ACWR 1줄 + 일반론 |
  | 왜 테이퍼하면 폼이 올라가? | general | TSB·등급 나열 + "API 키를 입력하세요" |
  | 이 폼이면 이번 주엔 뭘 하면 돼? | weekly | 주간 점수·거리 — 처방 없음 |
  | 남은 기간 주차별로 어떻게 준비할까? | training | 오늘 훈련 추천 — 주차별 계획 없음 |
  | 테이퍼는 언제부터 어떻게 할까?(D-21 이하) | training | 오늘 훈련 추천 |

- 근거: `frontend/src/lib/coachSuggestions.ts:11-30`(질문 생성), `chat_engine_rules.py:50-65`(분기). 스레드 1 msg4 "마라톤 거리별 예상시간은?" → race 분기 → "설정된 목표 레이스가 없습니다. **훈련 탭**에서 목표를 추가하세요"(v1 용어, 예측 시간 질문에 대한 답 없음).
- 왜 문제인가: 앱이 먼저 제안한 질문에 앱이 답하지 못한다. 러너는 "Coach는 쓸모없다"를 가장 짧은 경로로 배운다. 특히 "목표 기록 가능할까?"는 레이스 준비 러너의 핵심 질문이고, 답에 필요한 데이터(마라톤 예측 3:40:23 vs 목표 3:19:00, 예측 추이)가 이미 Today에 있다. U10.
- 개선안:
  - 추천 질문마다 **전용 규칙 핸들러**를 둔다. 추천 칩은 자유 텍스트가 아니라 `chip_id`로 보낸다(`chat()`은 이미 `chip_id`를 지원한다). 칩 → 핸들러 매핑을 단위 테스트로 고정한다.
  - "목표 기록 가능할까?" 핸들러의 최소 응답: 현재 예측(모델·신뢰 구간), 목표와의 차이(분/㎞ 페이스), 최근 4주 예측 추이 방향, 차이를 줄이는 데 필요한 조건(예: "마라톤 페이스 30km 이상 롱런 2회를 목표 페이스 ±5초로 소화"). 근거 칩은 예측 상세, 최근 롱런, CTL로 둔다.
  - 규칙으로 답할 수 없는 질문(테이퍼 원리 등)에는 "지금은 LLM이 연결되지 않아 이 질문에 답할 수 없습니다"라고 정직하게 답한다. 무관한 지표를 나열하지 않는다.

### [중요] F-DATA-06 컨디션 입력이 "자동 반영"되지 않는다 — 척도 방향도 반대로 읽힐 수 있다
- 현상:
  - Coach 홈 문구는 "입력한 컨디션은 Coach 답변에 자동으로 반영됩니다"(`coach/+page.svelte:225`)이다. 그러나 체크인을 읽는 곳은 LLM 컨텍스트(`chat_context.py:61`)뿐이고, 그 경로는 지금 100% 실패한다(F-DATA-04). 규칙 경로 `ai_context.build_context()`에는 체크인 키가 없다. Today 브리핑(`today_service.get_today_briefing`)과 코치 근거 칩에도 체크인이 없다.
  - DB `user_inputs`에 `checkin` 행이 0건이다. 이 계정은 한 번도 입력하지 않았거나 입력이 보존되지 않았다. 실제 반영 사례는 확인할 수 없었고, 코드 경로 기준으로는 반영되지 않는다.
  - 입력 UI(`coach-checkin-open-desktop.png`)는 "어떻게 느껴지나요?" 아래 1~10 버튼만 보여준다. 1과 10 중 어느 쪽이 좋은지 화면에 없다(`QuickInput.svelte:65-76`, "피로도"는 `aria-label`에만 있음). 저장된 값은 LLM에 "피로도 N/10"으로 전달된다(`chat_context_checkin.py:36`). "어떻게 느껴지나요?"에 10(최고)을 누르면 "피로도 10/10"이 되어 의미가 반대로 뒤집힌다. 통증 4단계에도 "통증"이라는 라벨이 화면에 없다.
- 왜 문제인가: 주관 피로·통증은 부하 지표가 보지 못하는 부상 초기 신호다. 코칭에서는 객관 지표보다 우선할 때가 많다. 반영되지 않는데 "반영된다"고 적는 것은 신뢰 문제이고, 척도 방향이 모호하면 입력한 데이터가 오히려 해가 된다. P6·P7, U5.
- 개선안:
  - 질문을 "오늘 피로도는? (1 상쾌 — 10 탈진)"으로 바꾸고 양 끝에 라벨을 표시한다. 통증에도 "통증" 제목과 부위 선택(선택 항목)을 둔다.
  - 규칙 답변과 Today 판정 함수(F-DATA-07)에 체크인을 입력으로 넣는다. 예: 피로 ≥8 또는 통증 ≥중간 → 강도 한 단계 하향, "통증 '중간' — 오늘 달리기 대신 교차훈련/휴식" 같은 명시적 우선 규칙. 반영되었을 때는 근거 칩 `체감 피로 7/10 (오늘 입력)`이 반드시 붙게 한다. 03e-coach.md 7절 목업의 `<EvidenceQuote src="체감 피로 어제 7/10"/>`이 설계 의도다.
  - 반영 경로가 생기기 전까지 문구는 "AI 연결 시 답변에 참고됩니다"로 사실대로 고친다.

### [중요] F-DATA-07 코칭 판정이 TSB 한 개와 버그 난 등급에 의존한다 — 부하·회복·레이스 국면·완료 세션이 통합되지 않는다
- 현상: 규칙 답변은 ① 회복 등급(버그), ② TSB 3구간 문장, ③ 오늘 계획 한 줄을 이어 붙인 것이다. 그 결과는 다음과 같다.
  - TSB -10.7 → "볼륨 줄이세요". CTL 71 러너가 빌드 국면에서 보이는 TSB -10~-20은 정상적인 생산적 부하 구간이다. Today도 -10~-20을 "피로 누적 — 가볍게"로 본다. 임계값은 두 화면이 비슷하지만 경계 연산자는 다르다(Coach `> -10`, Today `>= -10`, `today_service.py:21-29`).
  - ACWR(9/21~27: 1.2·1.0·0.8·1.0·1.1·1.0·1.1, 안전 범위), CIRS, 웰니스, 레이스 D-day, 오늘 이미 달렸는지는 판정에 쓰이지 않는다. 9/27 오늘은 9.3km를 이미 완료했지만(`activity_summaries` 17414), 코치는 여전히 "오늘 훈련"을 처방하는 구조다(`_respond_training_recommendation`은 `today_activity`를 보지 않음).
  - 9/24 msg8은 TSB -28.4(부하상 매우 피로)와 웰니스 최상(BB 100·HRV 97)이 충돌하는 상황이었다. 러너에게 가장 가치 있는 설명은 "몸은 회복됐지만 누적 부하가 크다 — 강도는 가능, 볼륨은 절제"처럼 두 신호를 조정하는 것이다. 실제 답은 둘 중 어느 쪽도 설명하지 않았다.
- 왜 문제인가: 비전의 "맥락 있는 안내"는 여러 신호를 조정한 결론 + 근거를 요구한다. 지표가 이미 DB에 다 있는데(ACWR·CIRS·UTRS·RRI·웰니스·계획 매칭) 코치가 그중 하나만 쓰면, 러너는 Garmin의 "훈련 준비도" 한 줄보다 나은 것을 얻지 못한다. P7, U10.
- 개선안: `src/services/readiness_decision.py`(가칭) 하나를 Today와 Coach가 함께 쓴다. 입력은 `tsb, acwr, cirs, recovery_score/grade, checkin, plan_today, completed_today, race_phase(D-day)`이고, 출력은 `{decision: key|easy|rest|done, intensity_cap, volume_hint, reasons[], caveats[]}`이다. 우선순위 규칙은 다음과 같다.
  1. 통증 중간 이상 → rest/교차
  2. 오늘 완료 → "오늘은 끝났습니다 — 내일 세션 준비" + 결과 요약
  3. ACWR > 1.5 또는 CIRS 고위험 → 볼륨 하향
  4. 웰니스 poor + TSB < -20 → easy
  5. 그 외 → 계획 유지

  국면별 TSB 해석(빌드: -10~-25 정상 / 테이퍼: 목표 +5~+20)을 reasons에 문장으로 넣는다. `reasons`/`caveats`가 곧 근거 칩이 된다(F-DATA-02).

### [개선] F-DATA-08 답변 본문 단위·포맷·용어 위반
- 현상·근거: msg10 `오늘 활동: 10.027959999999998km, 페이스 344.95초/km`(`chat_engine_rules.py:255-256`, 부동소수 원시값·초/km). `회복 등급: excellent/moderate`(영문 내부 키 노출). `오늘 계획: recovery 6.9km`(workout_type 영문). "훈련 탭에서 목표를 추가하세요"(v1 IA 용어). 칩 라벨 `TSB -11`과 본문 `TSB -10.7`의 반올림 자릿수도 다르다. `today_activity`는 `v_canonical_activities`가 아니라 `activity_summaries`에서 `start_time DESC LIMIT 1`로 고르기 때문에, 문자열 정렬상 `T` 표기인 intervals 행이 선택된다(`ai_context.py` build_context, 같은 활동의 duration이 garmin 3458s / intervals 3471s로 다름).
- 왜 문제인가: U3 위반이다. 원천 선택 규칙이 다른 화면(canonical)과 달라 P3 일관성이 깨진다.
- 개선안: 규칙 엔진 출력은 공용 포맷터(`format_distance`→`10.03km`, `format_pace`→`5:45/km`)를 쓴다. 등급과 운동 유형은 한국어 라벨 맵으로 바꾼다(excellent→매우 좋음, recovery→회복주). 본문과 칩은 같은 자릿수 규칙(TSB 정수)을 따른다. 오늘 활동은 `v_canonical_activities`에서 읽는다. "훈련 탭" → "Coach › 플랜".

### [개선] F-DATA-09 레이스 준비 근거 `레이스 아침 TSB +25 (테이퍼 시)`의 가정이 보이지 않는다
- 현상: 9/25 칩은 `+25`, 9/27 Today는 `+24`이고, 둘 다 `drill: null`이라 누를 수 없다. 어떤 테이퍼(기간·감량률)를 가정했는지, 목표 범위가 얼마인지 설명이 없다.
- 왜 문제인가: CTL ~71에서 레이스 아침 TSB +25는 ATL이 약 46까지 내려간다는 뜻이다. 마라톤에서 흔히 쓰는 +10~+25 범위의 상단이라, 러너에 따라서는 과한 테이퍼(체력 손실) 신호로 읽을 수 있다. 가정이 안 보이면 러너는 이 숫자로 테이퍼 결정을 할 수 없다. U5·U6.

## 잘된 점 (유지)

- **근거를 메시지 단위로 저장하는 구조**: `chat_messages.evidence_json`에 `value`와 `drill.scope_id`(날짜)가 들어간다. 스냅샷과 버전 필드만 추가하면 F-DATA-03을 해결할 수 있는 올바른 뼈대다.
- **드릴 시트가 답변 날짜를 기준으로 연다**: `scope_id=2026-09-25`로 조회하므로 "오늘 값"이 아니라 "그날 값"을 보여주는 방향은 맞다(다만 재계산 값이라는 표시가 필요하다).
- **"규칙 기반 답변" 라벨**: 최소한 LLM 답변이 아님을 숨기지는 않는다. 3상태 확장의 출발점이다.
- **목표 국면 인식 추천 질문**: `homeTopics()`가 D-21 이하에서는 테이퍼 질문으로, 목표 기록이 있으면 "목표 기록 가능할까?"로 바꾼다. 질문 선택은 코칭 관점에서 적절하다(문제는 답 경로, F-DATA-05).
- **동명 스레드 날짜 구분과 7일 경과 스레드의 "당시 기준" 표시**(`threadAge.ts`). 개념은 맞고 임계값만 조정하면 된다.
- **LLM 경로 설계**: 의도별 컨텍스트, 체크인 ±1일 보정(UTC/KST 어긋남 대응), MCP와 같은 도구 세트는 데이터 코치로서 좋은 설계다. 지금 문제는 연결 실패와 고지 부재다.
- 응답 속도: Coach 홈 FCP 0.47s, 스레드 열기 152ms, 근거 칩 패널 39ms(`02-performance.md`).

## 최우선 개선 3개

1. **판정 로직 수정 + 단일화**(F-DATA-01·07): 등급 상수 불일치를 고치고 회귀 테스트를 넣는다. 이어서 Today와 Coach가 함께 쓰는 `readiness_decision`(부하·회복·체크인·완료 여부·레이스 국면)을 만든다. "항상 쉬어라"를 없애는 것이 Coach 신뢰 회복의 전제다.
2. **근거 = 실제 입력, as-of 스냅샷**(F-DATA-02·03): 답변 생성기가 사용한 수치를 evidence로 반환하게 한다(supports/caveat). evidence에 `algorithm_version, computed_at`을 저장하고, 드릴 시트에 "당시 값 → 현재 값"을 함께 보여준다. 1일 경과 답변에는 as-of 라벨을 붙인다.
3. **LLM 상태 투명화 + P8 고지 + 체크인 연결**(F-DATA-04·05·06): 실패 원인을 보이는 3상태 출처 라벨과 연결 오류 배너를 두고, 입력 바 위에 전송 범위를 고지한다. 추천 칩은 `chip_id` 전용 핸들러로 보낸다. 체크인 척도에 방향 라벨을 달고 판정 입력으로 연결한다(연결 전까지 문구를 사실대로 고친다).
